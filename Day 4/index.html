Day 04 Distributed Caching & Redis

Caching with Redis

Even well-indexed database queries perform disk reads, query planning, and lock checks on every request. When thousands of users request the same catalog items, configuration, or dashboard summaries repeatedly, recomputing the exact same result wastes database capacity. Today you will learn how Redis caching works, how to design keys and TTLs safely, how invalidation prevents stale bugs, and how to integrate cache-aside caching into Express.

Connection to Days 2 & 3

Shared Redis caching keeps horizontally scaled Node instances stateless while slashing read latency from tens of milliseconds to ~1–2ms.

Core Principle

Caching is a controlled trade-off between speed and freshness. Every cached entry needs an explicit key design, TTL, and invalidation plan.

Practical Output

Implement a fault-tolerant Redis cache service and add cache-aside reads with write invalidation to an Express product API.

01. Foundation

What You Will Learn & Objectives

Redis (Remote Dictionary Server) is an in-memory key-value data store shared across backend instances. Because data lives in RAM and Redis executes commands on a single fast event loop without complex SQL joins or disk seeks on reads, lookups routinely finish in under a millisecond inside the same data center.

Implement Cache-Aside in Node.js and distinguish it from Read-Through and Write-Through architectures.

Guard against cache stampedes, cache penetration, cross-user data leaks, and blocking KEYS * scans.

02. Deep Dive

Core Caching & Redis Concepts

1. Why Caching Is Needed

Most real-world applications follow a skewed read pattern: 80–95% of traffic reads a relatively small subset of popular items (homepage feeds, product details, public profiles, exchange rates, feature flags). Caching stores the computed or queried result in fast RAM so repeated requests bypass heavy database joins, aggregations, or external third-party API calls.

Unlike Day 2's warning against in-memory Node.js Maps, Redis sits outside your web processes. Every horizontally scaled Express container reads and writes the exact same shared cache tier.

2. The Cache-Aside (Lazy Loading) Pattern

Cache-aside is the most common caching pattern in Node.js backends because your application code stays in full control:

  1. The service asks Redis for a key (e.g., v1:product:42).
  2. Cache Hit: Redis returns the serialized payload, and the API responds immediately without touching the database.
  3. Cache Miss: The service queries the primary database, writes the result into Redis with an expiration time (TTL), and returns the data.
  4. On Write/Update: The service updates the primary database and deletes (invalidates) the affected cache key so the next read fetches fresh data.

3. Read-Through and Write-Through Concepts

In Read-Through caching, the application talks only to a cache provider/library; on a miss, the cache layer itself knows how to fetch from the database, populate itself, and return the record.

In Write-Through caching, every database write goes synchronously through the cache layer, updating both the cache and the database before confirming success. This keeps cached reads consistently fresh, at the cost of slightly higher write latency and storing items in RAM that may never be read again unless paired with TTLs.

4. Cache Keys and Expiration

Well-structured keys prevent silent collisions and simplify debugging. Follow a predictable namespace convention including schema version, domain, and normalized parameters:

  • v1:product:65f1a9c2 — single entity key.
  • v1:catalog:cat=electronics:page=1:limit=20 — list/query key with sorted query parameters so ?page=1&cat=books and ?cat=books&page=1 reuse the same cache entry.
  • v1:user:891:permissions — user-scoped key (must include user or tenant ID!).

Including a version prefix like v1: allows instant logical invalidation across the entire app when you deploy a breaking response shape change—simply bump the prefix to v2:.

5. TTL and Cache Invalidation

Every cached key should have a Time To Live (TTL) (set via Redis EX or PX). TTL acts as both a memory safeguard (preventing unbounded RAM growth) and an upper bound on how long stale data can survive if an invalidation event fails.

Choose TTL based on staleness tolerance: 30 seconds for live dashboards, 5–15 minutes for product descriptions, or 24 hours for static country lists. When updating a record, prefer deleting the key (DEL) rather than updating its value blindly in Redis, because concurrent writes can overwrite each other out of order.

6. Redis Data Types at a Practical Level

Redis is far more capable than a plain JSON string store. Five foundational data types cover most backend needs:

Redis Type Key Commands Ideal Backend Use Cases
String GET, SET EX, INCR, SET NX Serialized JSON API responses, atomic rate-limit counters, distributed locks, idempotency keys
Hash HGET, HSET, HGETALL, HINCRBY Structured objects (user session attributes, shopping carts, feature flags) where single fields update independently
List LPUSH, RPOP, LRANGE, LTRIM Simple job queues, capped recent activity feeds (last 20 notifications)
Set SADD, SISMEMBER, SREM Unique tags, active user IDs in a room, token revocation checks
Sorted Set (ZSET) ZADD, ZRANGE, ZREMRANGEBYSCORE Leaderboards, priority queues, sliding-window rate limiters scored by timestamp

7. Caching API Responses vs. Service-Layer Data

You can cache at the HTTP response middleware level (keyed by method + normalized URL) or at the service/repository level (caching domain objects like product details or user permissions).

Service-layer caching is usually more flexible: multiple endpoints (for example, product detail page, cart validator, and invoice builder) all benefit from the same cached product lookup, and invalidation happens cleanly right where writes occur. HTTP middleware caching works best for public, unauthenticated read endpoints with identical responses for everyone.

8. Cache Consistency & Common Failure Modes

  • Cache Stampede (Thundering Herd): When a popular key expires, 500 concurrent requests miss at once and all 500 hammer the database simultaneously. Mitigate with TTL jitter (adding random ±10% seconds to TTL), mutex/single-flight locking, or background pre-refresh.
  • Cache Penetration: Malicious or buggy clients repeatedly request non-existent IDs (/products/invalid-999). Every lookup misses Redis and hits the database. Fix by caching a short-TTL null sentinel (e.g., 30s) or validating ID format before querying.
  • Thundering Eviction: Under memory pressure, Redis evicts keys according to its maxmemory-policy (commonly allkeys-lru or volatile-lru for pure caches). Never store irreplaceable primary data in a Redis instance configured with an eviction policy.
03. Mechanics

Cache Hit, Miss, and Invalidation Flow

  1. Normalize Key: Construct a deterministic key (e.g., v1:product:p_104) before querying Redis.
  2. Attempt Redis Read (Fail-Open): Call redis.get(key) inside a try/catch with a tight command timeout. If Redis is temporarily unreachable, log a warning and fall through to the database rather than returning 500 errors.
  3. Hit Path: Parse JSON and return immediately, optionally attaching an observability header like X-Cache: HIT during testing/staging.
  4. Miss Path: Query the primary database, store the serialized result in Redis with SET key value EX ttlWithJitter, and return the response (X-Cache: MISS).
  5. Write Invalidation: After a successful PATCH or DELETE commits to the primary database, call redis.del(key) so stale values are cleared immediately.

05. Step-by-Step Implementation

Adding Redis Cache-Aside to an Express API

Following Day 1's architecture principles, we isolate Redis behind a dedicated CacheService and inject it into our product service. Notice how every Redis operation is wrapped safely so a Redis hiccup never breaks API availability.

Step 1: Build a Fault-Tolerant Cache Service with TTL Jitter

src/shared/cache/cache.service.js 
import { createClient } from 'redis';

export async function createRedisConnection() {
  const client = createClient({
    url: process.env.REDIS_URL,
    socket: {
      connectTimeout: 3000,
      reconnectStrategy: (retries) => Math.min(retries * 100, 3000)
    }
  });

  client.on('error', (err) => {
    console.error('Redis client error:', err.message);
  });

  await client.connect();
  return client;
}

export class CacheService {
  constructor(redisClient, namespace = 'v1') {
    this.redis = redisClient;
    this.namespace = namespace;
  }

  buildKey(rawKey) {
    return `${this.namespace}:${rawKey}`;
  }

  withJitter(baseTtlSeconds) {
    const jitterWindow = Math.max(1, Math.floor(baseTtlSeconds * 0.1));
    const offset = Math.floor(Math.random() * jitterWindow);
    return baseTtlSeconds + offset;
  }

  async getJson(rawKey) {
    if (!this.redis || !this.redis.isReady) {
      return null;
    }
    try {
      const cached = await this.redis.get(this.buildKey(rawKey));
      return cached ? JSON.parse(cached) : null;
    } catch (err) {
      return null;
    }
  }

  async setJson(rawKey, value, ttlSeconds = 300) {
    if (!this.redis || !this.redis.isReady) {
      return;
    }
    try {
      const ttl = this.withJitter(ttlSeconds);
      await this.redis.set(this.buildKey(rawKey), JSON.stringify(value), { EX: ttl });
    } catch (err) {
    }
  }

  async del(rawKey) {
    if (!this.redis || !this.redis.isReady) {
      return;
    }
    try {
      await this.redis.del(this.buildKey(rawKey));
    } catch (err) {
    }
  }
}

Step 2: Integrate Cache-Aside & Invalidation in the Service Layer

src/modules/products/product.service.js 
import { AppError } from '../../shared/errors/AppError.js';

export class ProductService {
  constructor({ productRepository, cacheService }) {
    this.productRepository = productRepository;
    this.cacheService = cacheService;
  }

  productKey(productId) {
    return `product:${productId}`;
  }

  async getProductById(productId) {
    const cacheKey = this.productKey(productId);
    const cached = await this.cacheService.getJson(cacheKey);
    if (cached !== null) {
      if (cached.__notFound) {
        throw new AppError('Product not found', 404, 'PRODUCT_NOT_FOUND');
      }
      return { product: cached, cacheStatus: 'HIT' };
    }

    const product = await this.productRepository.findById(productId);
    if (!product) {
      await this.cacheService.setJson(cacheKey, { __notFound: true }, 30);
      throw new AppError('Product not found', 404, 'PRODUCT_NOT_FOUND');
    }

    await this.cacheService.setJson(cacheKey, product, 300);
    return { product, cacheStatus: 'MISS' };
  }

  async updateProduct(productId, updates) {
    const updated = await this.productRepository.updateById(productId, updates);
    if (!updated) {
      throw new AppError('Product not found', 404, 'PRODUCT_NOT_FOUND');
    }

    await this.cacheService.del(this.productKey(productId));
    return updated;
  }
}

Step 3: Expose Cache Status cleanly in the Express Controller

src/modules/products/product.controller.js 
export class ProductController {
  constructor(productService) {
    this.productService = productService;
  }

  getOne = async (req, res, next) => {
    try {
      const { product, cacheStatus } = await this.productService.getProductById(req.params.id);
      res.set('X-Cache', cacheStatus);
      res.status(200).json({ status: 'success', data: product });
    } catch (err) {
      next(err);
    }
  };

  patchOne = async (req, res, next) => {
    try {
      const updated = await this.productService.updateProduct(req.params.id, req.body);
      res.status(200).json({ status: 'success', data: updated });
    } catch (err) {
      next(err);
    }
  };
}

Key Code Sections Explained

  • Fail-Open Guard (if (!this.redis || !this.redis.isReady)): A cache is an optimization, not a single point of failure. If Redis restarts, read traffic safely degrades to database queries.
  • TTL Jitter (withJitter): Spreads expiration times slightly so 1,000 keys populated during a startup burst do not expire on the exact same second.
  • Negative Caching ({ __notFound: true } for 30s): Prevents repeated requests for missing product IDs from hammering the database (mitigating cache penetration). Just remember to call del if a missing key is later created!
  • Write-Then-Delete Order: Updating the database first and deleting the cache key second narrows the window for stale data compared to updating the cache directly.
06. Engineering Judgment

Pattern Comparison & When to Cache

Pattern Read Path Write Path Trade-Offs
Cache-Aside App checks Redis, falls back to DB, populates Redis App writes DB, deletes cache key Simple, resilient, only caches requested items; brief window of stale data possible on concurrent writes
Read-Through App queries cache provider; provider loads DB on miss Depends on write policy (often paired with write-through) Cleaner app code, requires cache-aware plugin/proxy layer
Write-Through Reads hit warm cache frequently Cache writes synchronously to DB and updates itself Stronger cache freshness, slower writes and wastes RAM on rarely read writes unless TTLs prune cold keys

Great Candidates for Redis Caching

  • Product catalogs, blog posts, public profiles, and configuration settings.
  • Expensive analytics aggregations that can tolerate 1–5 minutes of staleness.
  • Authenticated user permission maps (keyed by userId and invalidated on role changes).
  • External third-party API responses (currency rates, weather, geocoding).

Poor Candidates (Do NOT Cache Blindly)

  • Real-time financial account balances or inventory stock checks during checkout (must be atomic in DB!).
  • Write-heavy data that mutates faster than it is read (cache hit ratio stays near 0%).
  • Sensitive user-private endpoints unless user/tenant ID is explicitly part of the cache key.
07. Production Readiness

Common Mistakes, Security & Reliability

Mistake 1: Running KEYS pattern* to Invalidate Lists in Production

Availability risk: Redis executes commands sequentially on one main thread. Scanning 1,000,000 keys with KEYS * blocks every Redis client in the entire cluster for hundreds of milliseconds or seconds.

Fix: Track explicit keys, use versioned prefix keys (bump a catalog epoch number stored in Redis), or use non-blocking cursor-based SCAN sparingly.

Mistake 2: Omitting User/Tenant ID from Personalized Cache Keys

Critical Security leak: Caching GET /api/orders under cache:orders:page=1 returns User A's private orders to User B!

Fix: Always include userId or tenantId in keys for non-public data, and never apply generic public HTTP cache middleware to authenticated routes without scoping.

Mistake 3: Forgetting TTLs or Unbounded Key Growth

Reliability risk: Keys without expiration accumulate until Redis hits maxmemory and either rejects writes or evicts critical session keys if shared on the same instance.

Fix: Always set explicit TTLs on cache keys and separate ephemeral cache Redis instances from durable session/queue Redis instances when workloads grow.

Mistake 4: Caching Unnormalized Query Parameter Combinations

Efficiency risk: Treating raw req.originalUrl as a key means ?sort=asc&page=1 and ?page=1&sort=asc create duplicate entries and slash your cache hit ratio.

Fix: Whitelist allowed query parameters, apply defaults, and sort parameter names deterministically before building the key.

10. Active Recall

Short-Answer Review Questions

A cache stampede happens when a popular existing key expires and many concurrent requests miss simultaneously, all querying the database at once to recompute it. Cache penetration happens when requests target non-existent keys that are never cached, causing every single request to bypass Redis and hit the database.

Use a Redis Hash when you frequently need to read or atomically increment individual fields of an object (like a cart item quantity or user session flags via HINCRBY / HGET) without downloading, parsing, modifying, and re-serializing the entire JSON blob.

Sorting parameters ensures ?cat=books&page=2 and ?page=2&cat=books map to one shared key instead of duplicating cache entries. Whitelisting ignores arbitrary tracking parameters (like ?utm_source=... or random cache-buster strings) that would otherwise fragment the cache and allow attackers to fill Redis memory.

Under allkeys-lru, when memory fills up, Redis can evict any key—including active queue jobs, distributed locks, or session tokens! Caches should use eviction policies on dedicated cache instances, while queues and durable state belong on Redis instances configured with noeviction and persistence.

Stock availability changes rapidly and requires strict transactional consistency to prevent overselling. A 5-minute cached stock count would allow customers to purchase items that already sold out seconds earlier; checkout reservations must happen atomically against the primary database.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: A developer added caching middleware to GET /api/orders using const key = `cache:${req.originalUrl}`. Identify the two serious bugs and write a safe key builder function.

Reference Solution 
export function buildOrdersCacheKey({ userId, query }) {
  const status = typeof query.status === 'string' ? query.status.trim() : 'all';
  const page = Math.max(1, Number.parseInt(query.page, 10) || 1);
  const limit = Math.min(50, Math.max(1, Number.parseInt(query.limit, 10) || 20));
  return `v1:user:${userId}:orders:limit=${limit}:page=${page}:status=${status}`;
}

Bugs fixed: (1) Scoped key by userId so users never read each other's orders; (2) whitelisted, defaulted, and clamped query parameters in canonical alphabetical order so random query strings cannot pollute Redis memory or lower hit rates.

Problem: Write a getOrLoadSingleFlight(key, ttlSeconds, loaderFn) method that deduplicates concurrent cache-miss database calls within a Node.js instance using an in-flight Promise map before writing to Redis.

Reference Solution 
export class CoalescingCache extends CacheService {
  constructor(redisClient, namespace = 'v1') {
    super(redisClient, namespace);
    this.inFlight = new Map();
  }

  async getOrLoad(rawKey, ttlSeconds, loaderFn) {
    const cached = await this.getJson(rawKey);
    if (cached !== null) {
      return cached;
    }

    if (this.inFlight.has(rawKey)) {
      return this.inFlight.get(rawKey);
    }

    const loadPromise = (async () => {
      try {
        const freshValue = await loaderFn();
        await this.setJson(rawKey, freshValue, ttlSeconds);
        return freshValue;
      } finally {
        this.inFlight.delete(rawKey);
      }
    })();

    this.inFlight.set(rawKey, loadPromise);
    return loadPromise;
  }
}

Problem: You cache paginated product lists under keys like v1:products:page=1:sort=price, page=2, and 15 filter combinations. When an admin adds or edits a product, deleting every unknown filter combination is hard. Design an O(1) invalidation approach without KEYS *.

Reference Architecture: Use a namespace epoch / generation counter stored in Redis (e.g., epoch:products = 17). Every list cache key embeds that epoch: v1:products:e17:page=1:sort=price. When an admin updates or creates any product, execute a single INCR epoch:products (now 18). All subsequent list reads automatically look up e18 keys and miss cleanly, while old e17 keys expire automatically via their TTL!

12. Takeaways

Day 4 Revision Summary

  • Redis provides fast, shared in-memory storage across stateless Express replicas.
  • Cache-Aside checks Redis first, loads DB on miss with TTL, and invalidates via DEL on writes.
  • Key design requires namespace versions, canonical sorted parameters, and explicit user/tenant scoping for private data.
  • Redis types (String, Hash, List, Set, ZSET) solve distinct caching, counter, and ranking tasks cleanly.
  • Resilience means failing open if cache is unreachable, adding TTL jitter, guarding against penetration, and never running KEYS * in production.
