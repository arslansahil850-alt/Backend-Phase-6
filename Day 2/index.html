Day 02 Scalability & Distributed Design

Scalable Backend Systems

An API that responds in 25ms for a single developer on localhost can grind to a halt—or corrupt user sessions—when traffic spikes to thousands of concurrent requests across multiple servers. Today you will learn how scalable backends handle growing load through stateless design, load balancing, shared state, capacity planning, and database scaling awareness.

Connection to Day 1

Layered separation and Dependency Injection allow you to swap local in-memory adapters for shared Redis or cloud storage without rewriting business services.

Core Mental Shift

Never assume only one Node.js process is running, or that a server's local RAM and disk will still exist on the next request.

Practical Output

Audit a sample Express API, pinpoint every state and concurrency bottleneck preventing horizontal scaling, and design stateless replacements.

01. Foundation

What You Will Learn & Objectives

Scalability is not simply "being fast today." A scalable system maintains acceptable response times and reliability as workload, concurrent users, or stored data volume increase—ideally by adding resources proportionally rather than rewriting the application.

02. Deep Dive

Core Scalability Concepts

1. Scalability Fundamentals: Throughput, Latency & Tail Behavior

To reason about scale, separate three core metrics:

  • Throughput (RPS / QPS): How many requests or queries the system completes per second.
  • Latency: How long a single request takes from arrival to response. Always inspect percentiles such as p95 and p99 (the slowest 5% or 1% of requests), not just averages, because averages hide severe queuing stalls.
  • Concurrency: How many requests are actively in-flight at the exact same instant.

When load exceeds capacity, requests queue up, latency climbs exponentially, and timeouts trigger client retries that multiply load further—a phenomenon known as a cascading overload.

2. Vertical Scaling vs. Horizontal Scaling

Vertical scaling (scaling up) adds more CPU cores, RAM, or faster NVMe storage to a single server. It requires almost zero code changes and keeps data local, making it very attractive early on. However, a single Node.js process is single-threaded for JavaScript execution—simply buying a 32-core machine will not help a single Node process unless you run multiple worker processes (e.g., via PM2, containers, or orchestration). Vertical scaling also hits hardware ceilings and leaves a single point of failure.

Horizontal scaling (scaling out) runs multiple identical backend instances behind a load balancer. It improves fault tolerance (if one node crashes, others continue serving) and enables elastic autoscaling, but requires every backend instance to be stateless.

3. Stateless Backend Design

A backend instance is stateless when it stores no client-specific session data, user uploads, rate-limit counters, or job state in its own process memory or local filesystem between requests. Every HTTP request contains everything needed to identify and authorize the caller (such as a token or session ID), and any persistent or shared ephemeral state lives in an external store (PostgreSQL, MongoDB, Redis, or S3-compatible object storage).

If an API relies on local RAM—for example, const activeSessions = new Map()—it fails immediately once you run two instances behind a round-robin load balancer: Request 1 logs the user in on Instance A, and Request 2 hits Instance B, which rejects the user as unauthenticated.

4. Load Balancing Concepts

A load balancer sits between clients and your pool of backend instances, distributing incoming traffic and removing unhealthy instances automatically.

  • Layer 4 (Transport) vs. Layer 7 (Application): L4 balances raw TCP/UDP connections quickly without inspecting HTTP payloads. L7 inspects HTTP paths, headers, and cookies, enabling TLS termination, path-based routing, and request-level distribution.
  • Distribution Algorithms: Round-robin cycles evenly across servers; Least connections routes to the instance with the fewest active requests (better when request durations vary widely); IP Hash tries to pin a client IP to one server.
  • Health Checks & Draining: Load balancers poll endpoints such as GET /health or GET /ready. Before shutting down an instance during deployment, the server must stop accepting new connections while finishing in-flight requests (graceful shutdown).
  • Proxy Headers: Behind a load balancer, req.ip sees the balancer's private IP unless Express enables trust proxy and reads X-Forwarded-For / X-Forwarded-Proto safely.

5. Handling Concurrent Requests

Node.js handles high I/O concurrency efficiently via its non-blocking event loop, but concurrency still creates subtle scaling bugs:

  • Check-Then-Act Race Conditions: Reading a balance or coupon count in one query and updating it in another fails when two requests execute concurrently across two Node instances. Use atomic database operations or transactions.
  • Unbounded Fan-Out: Calling Promise.all(items.map(fetchExternal)) on 5,000 items simultaneously can exhaust sockets or trigger upstream rate bans. Bound concurrency using pools or queues.
  • Duplicate Retries: Mobile clients and load balancers retry timed-out requests. Write endpoints like payments or order creation need idempotency keys so retries do not duplicate side effects.

6. Bottlenecks and Capacity Planning

A system is only as fast as its narrowest bottleneck. Doubling from 4 to 8 Express containers often improves throughput by 0% if all 8 containers share a saturated database CPU, an unindexed collection scan, or a tiny connection pool.

Capacity planning estimates peak load before failure occurs using concrete numbers:

Applying Little's Law Conceptually

Concurrency (L) = Arrival Rate (λ) × Average Processing Time (W). If your endpoint receives 500 requests/sec and each request takes 0.2 seconds (200ms) end to end, your backend holds 500 × 0.2 = 100 requests concurrently in flight. Reducing average latency from 200ms to 40ms drops concurrent in-flight pressure from 100 down to 20—freeing database connections and memory without buying extra servers.

7. Database and Application Scaling Considerations

Stateless Express servers are trivial to scale out; databases are the hardest tier to scale because they hold durable state.

  • Connection Pooling: Opening a fresh TCP + TLS + auth handshake per query destroys performance. Each Node instance keeps a bounded connection pool (e.g., 10–20 connections). Watch the math: 20 Express instances × 50 pool size = 1,000 database connections, which can overwhelm PostgreSQL unless capped or routed through a pooler like PgBouncer.
  • Read Replicas: Most applications are read-heavy (e.g., 80–95% reads). Route read queries to follower replicas while directing writes to the primary node, keeping replication lag in mind (a user reading their own just-created record might briefly miss it on an asynchronous replica).
  • Vertical Scaling, Caching, and Sharding: Optimize indexes and queries first, offload hot reads to Redis (Day 4), scale the DB vertically, and consider horizontal sharding/partitioning only when single-node write throughput or storage capacity is truly exhausted.

8. Stateless Sessions and Shared State

Every piece of state an application needs falls into one of three categories and must live in the right tier:

  • Signed/Encrypted Client Tokens (JWT): Stateless authentication claims carried in headers or secure cookies—zero lookup per request, though revocation requires short TTLs or a shared denylist (covered in Day 8).
  • Shared Ephemeral State (Redis): Server-side session stores, distributed rate-limit counters, verification codes, and WebSocket pub/sub adapters.
  • Shared Durable State (Database & Object Storage): Relational/document records in primary databases and user-uploaded images/PDFs in S3-compatible object storage rather than local server folders.
03. Mechanics

How a Horizontally Scaled Request Travels

  1. DNS & Edge Routing: Client resolves the API domain to the load balancer's public IP address.
  2. TLS Termination & Forwarding: Load balancer terminates HTTPS, attaches X-Forwarded-For and X-Forwarded-Proto, and picks a healthy Node.js instance via least-connections.
  3. Stateless Processing: The chosen Express instance validates the token/session against shared Redis (or verifies JWT signature locally), executes business rules, and avoids touching local disk or process-wide mutable caches.
  4. Shared Data Tier: Database queries use bounded connection pools; uploaded files stream directly to object storage; background tasks push jobs to a shared queue instead of running inside the web process.
  5. Health & Autoscaling Loop: Metrics (CPU, memory, event-loop lag, HTTP 5xx rate) inform the orchestrator when to add or drain instances cleanly.

05. Step-by-Step Code Audit

Identifying & Fixing Scalability Blockers in Express

Inspect the sample Express server below. On a developer laptop with one process and 5 requests per minute, everything passes tests. Under production scaling across 4 containers, multiple components fail or bottleneck severely.

Anti-Pattern: Non-Scalable Express API 
import express from 'express';
import fs from 'node:fs/promises';
import path from 'node:path';
import crypto from 'node:crypto';

const app = express();
app.use(express.json());

const sessions = new Map();
const requestCounts = new Map();

app.use((req, res, next) => {
  const ip = req.socket.remoteAddress;
  const count = (requestCounts.get(ip) || 0) + 1;
  requestCounts.set(ip, count);
  if (count > 100) {
    return res.status(429).json({ error: 'Too many requests' });
  }
  next();
});

app.post('/login', (req, res) => {
  const sessionId = crypto.randomUUID();
  sessions.set(sessionId, { userId: req.body.userId, createdAt: Date.now() });
  res.cookie('sid', sessionId, { httpOnly: true }).json({ ok: true });
});

app.post('/avatar', async (req, res) => {
  const filePath = path.join(process.cwd(), 'uploads', `${Date.now()}.bin`);
  await fs.writeFile(filePath, Buffer.from(req.body.base64, 'base64'));
  res.json({ filePath });
});

app.get('/reports/summary', (req, res) => {
  let total = 0;
  for (let i = 0; i < 2e9; i += 1) {
    total += i % 7;
  }
  res.json({ total });
});

setInterval(() => {
  console.log('Running daily billing cleanup...');
}, 86400000);

app.listen(process.env.PORT || 3000);

What Prevents This API from Scaling?

  1. In-memory sessions Map: Breaks across multiple instances and loses all logged-in users on restart or deployment. It also leaks memory forever because old entries never expire.
  2. In-memory requestCounts Map & raw remoteAddress: Behind a load balancer, req.socket.remoteAddress is the load balancer's IP, so every user shares one counter and locks everyone out after 100 requests. Even with real client IPs, each server counts separately and leaks memory endlessly.
  3. Local filesystem ./uploads/ write: An avatar saved on Instance 1 returns 404 when requested from Instance 2, and container restarts wipe ephemeral disks.
  4. Synchronous CPU loop in /reports/summary: Blocks the Node.js event loop for seconds, freezing health checks and unrelated routes on the same instance.
  5. Inline setInterval billing job: Scaling to 6 web instances runs the billing cleanup 6 times simultaneously, risking duplicate charges.
  6. Missing graceful shutdown & readiness probe: Rolling deployments kill active HTTP connections mid-flight.

Refactored Stateless & Load-Balancer-Ready Express Setup

Below is the refactored application shell showing proxy trust, shared Redis session/rate-limit interfaces (via Day 1 dependency injection), readiness health checks, and graceful SIGTERM draining.

src/server.js — Stateless, Proxy-Aware, Graceful Shutdown 
import express from 'express';
import session from 'express-session';
import RedisStore from 'connect-redis';
import { createClient } from 'redis';

export async function createScalableApp({ dbPool, objectStorage }) {
  const app = express();

  app.set('trust proxy', 1);
  app.use(express.json({ limit: '1mb' }));

  const redisClient = createClient({ url: process.env.REDIS_URL });
  await redisClient.connect();

  app.use(
    session({
      store: new RedisStore({ client: redisClient, prefix: 'sess:' }),
      secret: process.env.SESSION_SECRET,
      resave: false,
      saveUninitialized: false,
      cookie: {
        httpOnly: true,
        secure: process.env.NODE_ENV === 'production',
        sameSite: 'lax',
        maxAge: 1000 * 60 * 60 * 24
      }
    })
  );

  app.get('/health', (req, res) => {
    res.status(200).json({ status: 'ok' });
  });

  app.get('/ready', async (req, res) => {
    try {
      await redisClient.ping();
      await dbPool.query('SELECT 1');
      res.status(200).json({ status: 'ready' });
    } catch (err) {
      res.status(503).json({ status: 'not_ready' });
    }
  });

  app.post('/avatar-upload-url', async (req, res, next) => {
    try {
      const signedUrl = await objectStorage.createPresignedUpload({
        userId: req.session.userId,
        contentType: req.body.contentType
      });
      res.status(200).json({ uploadUrl: signedUrl });
    } catch (err) {
      next(err);
    }
  });

  return { app, redisClient };
}

export function attachGracefulShutdown(server, { redisClient, dbPool }) {
  const shutdown = async (signal) => {
    console.log(`Received ${signal}, draining connections...`);
    server.close(async () => {
      await redisClient.quit();
      await dbPool.end();
      process.exit(0);
    });

    setTimeout(() => {
      process.exit(1);
    }, 10000).unref();
  };

  process.on('SIGTERM', () => shutdown('SIGTERM'));
  process.on('SIGINT', () => shutdown('SIGINT'));
}

Key Code Sections Explained

  • app.set('trust proxy', 1): Tells Express to trust the first reverse proxy hop (the load balancer) so req.ip, req.protocol, and secure cookies work accurately. Never set trust proxy blindly to true on internet-exposed servers without a trusted proxy, or clients can spoof X-Forwarded-For.
  • /health vs. /ready: Liveness (/health) confirms the process event loop is alive; readiness (/ready) checks critical dependencies (Redis/DB) before the load balancer sends live traffic.
  • Graceful SIGTERM Shutdown: server.close() stops accepting new TCP connections while allowing in-flight requests to finish before closing Redis and DB pools.
  • Presigned Object Storage URL: Offloads heavy binary file bytes away from Node.js API servers directly to cloud object storage.
06. Engineering Judgment

Use Cases, Alternatives, and Trade-Offs

Dimension Vertical Scaling (Scale Up) Horizontal Scaling (Scale Out)
Application Complexity Low — works even with single-node memory caches Higher — requires stateless design, shared Redis, external files
Availability & Fault Tolerance Single machine = single point of failure High — surviving instances absorb traffic if one node fails
Cost & Elasticity Steep hardware cost jumps; downtime during resize Pay-as-you-go autoscaling during traffic peaks and troughs
Node.js Suitability Requires cluster/multi-process workers to use multiple CPU cores Natural fit via containerized stateless replicas behind a load balancer

Sticky Sessions vs. Shared Stateless Sessions

Sticky sessions (session affinity) force a load balancer to route a user back to the same backend instance via a cookie or IP hash. Avoid relying on sticky sessions for REST APIs: they create uneven load distribution, fail when an instance restarts or scales down, and mask stateful bugs. Reserve session affinity only for legacy apps or specialized WebSocket handshakes when no shared adapter exists.

When to Optimize Before Scaling Out

Adding 10 extra Express instances to fix an N+1 query or missing database index wastes money and punishes the database harder. Always profile slow endpoints (Day 3) and add indexes/caching (Days 4 and 10) alongside horizontal scaling.

07. Production Readiness

Common Mistakes, Security & Reliability

Mistake 1: Blindly Setting app.set('trust proxy', true)

Security risk: If your server can also be reached bypassing the load balancer, an attacker can forge X-Forwarded-For headers to bypass IP rate limiters.

Fix: Specify the exact proxy hop count (e.g., 1) or trusted subnet CIDR, and restrict direct public access to backend instances using firewall/VPC rules.

Mistake 2: Exhausting Database Connections Across Scaled Replicas

Reliability risk: Increasing API containers from 2 to 20 multiplies total connection pool slots by 10x, crashing PostgreSQL or exhausting MongoDB connection limits.

Fix: Calculate maxInstances × poolSize < dbMaxConnections and use connection poolers where appropriate.

Mistake 3: Running Scheduled Cron Jobs Inside Every Web Container

Data integrity risk: Every scaled replica triggers the same email, invoice, or cleanup job simultaneously.

Fix: Separate scheduled workers from HTTP web processes, or use distributed locks / centralized job queues (Day 5).

Mistake 4: Missing Timeouts on Outbound Calls

Availability risk: A slow third-party payment or webhook API hangs Node promises indefinitely, exhausting memory and socket descriptors across all instances.

Fix: Set explicit connect and request timeouts (e.g., AbortSignal.timeout(5000)) and bound concurrency.

10. Active Recall

Short-Answer Review Questions

Layer 4 (Transport) load balancing routes packets based on IP addresses and TCP/UDP ports with very low overhead. Layer 7 (Application) load balancing parses HTTP headers, URLs, and cookies, enabling TLS termination, path-based microservice routing, and intelligent HTTP health checks.

Other horizontally scaled instances cannot read files saved to one container's local disk, and container restarts or redeployments erase ephemeral storage. Object storage (e.g., S3-compatible buckets) provides durable, globally addressable storage across all instances.

A liveness probe checks whether the Node.js process is running and responsive so the orchestrator knows if it needs restarting. A readiness probe checks whether downstream dependencies (database pool, Redis) are reachable so the load balancer only routes live traffic once the instance can actually serve requests.

If the true bottleneck is a saturated database, lock contention, or an overloaded third-party API, extra web instances generate more concurrent queries and open more connection pools, increasing lock waits and timeouts on the shared bottleneck.

An idempotency key is a unique client-generated token sent with a mutating request (e.g., Idempotency-Key header). The backend stores the key and outcome in a shared store (Redis/DB) so if network timeouts cause the client or load balancer to retry the exact request, the server returns the original outcome without charging or creating duplicate records.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: A batch sync endpoint runs await Promise.all(users.map((u) => fetchCrmProfile(u.id))) for 2,500 users at once, causing socket exhaustion and 502 errors from the CRM. Rewrite a bounded-concurrency helper in plain JavaScript that caps simultaneous in-flight promises to concurrency = 10.

Reference Solution 
export async function mapWithConcurrency(items, concurrency, workerFn) {
  const results = new Array(items.length);
  let nextIndex = 0;

  async function runWorker() {
    while (nextIndex < items.length) {
      const current = nextIndex;
      nextIndex += 1;
      results[current] = await workerFn(items[current], current);
    }
  }

  const workerCount = Math.min(concurrency, items.length);
  const workers = Array.from({ length: workerCount }, () => runWorker());
  await Promise.all(workers);
  return results;
}

Problem: Sketch an Express middleware using an injected Redis client that checks an Idempotency-Key header for POST /payments, prevents concurrent duplicate execution using atomic SET ... NX EX, and caches the JSON response for 10 minutes.

Reference Solution 
export function createIdempotencyMiddleware(redisClient, ttlSeconds = 600) {
  return async (req, res, next) => {
    const key = req.get('Idempotency-Key');
    if (!key) {
      return res.status(400).json({ error: 'Idempotency-Key header required' });
    }

    const storageKey = `idem:${req.user.id}:${key}`;
    const existing = await redisClient.get(storageKey);
    if (existing) {
      const parsed = JSON.parse(existing);
      if (parsed.status === 'processing') {
        return res.status(409).json({ error: 'Request already in progress' });
      }
      return res.status(parsed.httpStatus).json(parsed.body);
    }

    const locked = await redisClient.set(
      storageKey,
      JSON.stringify({ status: 'processing' }),
      { NX: true, EX: 60 }
    );
    if (!locked) {
      return res.status(409).json({ error: 'Concurrent duplicate request' });
    }

    const originalJson = res.json.bind(res);
    res.json = (body) => {
      redisClient
        .set(
          storageKey,
          JSON.stringify({ status: 'done', httpStatus: res.statusCode, body }),
          { EX: ttlSeconds }
        )
        .catch(() => {});
      return originalJson(body);
    };

    next();
  };
}

Problem: Your API normally serves 150 req/sec on 2 containers (pool size 15 each). An upcoming campaign expects 1,200 req/sec (80% reads, 20% writes). Your PostgreSQL primary maxes out at 200 connections. Design a scaling plan.

Reference Architecture: (1) Profile and cache top hot read endpoints in Redis (absorbing a large fraction of the 960 read req/s before hitting DB), (2) attach 1–2 PostgreSQL read replicas for uncached read traffic, (3) place a connection pooler like PgBouncer in transaction mode between scaled containers and PostgreSQL so 10–12 stateless Express containers stay safely beneath the 200-connection limit, and (4) configure autoscaling triggers on CPU, event-loop delay, and request latency with a readiness probe and graceful shutdown.

12. Takeaways

Day 2 Revision Summary

  • Vertical scaling buys simplicity early; horizontal scaling delivers resilience and elasticity once instances are stateless.
  • Stateless backends move sessions and counters to Redis, files to object storage, and durable records to shared databases.
  • Load balancers need proper health/readiness probes, trusted proxy configuration, and graceful SIGTERM connection draining.
  • Concurrency safety requires atomic DB updates, bounded outbound concurrency, timeouts, and idempotency keys.
  • Database tier limits (connection pool math, read replicas, replication lag) usually become the primary bottleneck as web nodes scale out.
