Day 10 Data Engineering & Persistence

Advanced Database Optimization

Caching and horizontal API scaling cannot fix slow, unindexed database writes, lock contention, or flawed data modeling. Today you will learn how database indexes work internally, how to design compound indexes with the ESR rule, how to read query execution plans, how to guarantee data integrity with atomic operations and transactions, how to optimize connection pools and MongoDB aggregations, and when relational SQL databases outperform NoSQL document stores.

Connection to Days 2, 3 & 4

Databases are the stateful bottleneck of scaled backends. Fast indexed queries protect connection pools and cut tail latency on cache misses.

Core Principle

Inspect real execution plans (explain / EXPLAIN ANALYZE) so databases scan dozens of index keys instead of millions of documents.

Practical Output

Diagnose slow queries in a sample API using execution stats, add compound ESR indexes, replace N+1 loops, and wrap multi-record transfers in transactions.

02. Deep Dive

Core Database Optimization Concepts

1. Database Indexes and Index Selection

Without an index, finding { email: 'ali@example.com' } forces a Collection Scan (COLLSCAN) or Full Table Scan—reading every record on disk/RAM in O(N) time. A B-Tree index stores sorted key pointers so lookups locate matching records in O(log N) time.

Index selection favors high-cardinality (selective) fields—such as userId, email, or orderNumber—over low-cardinality booleans like isActive alone. Remember the trade-off: every index speeds up matching reads while slowing down writes (INSERT, UPDATE, DELETE) and consuming RAM, because every index must stay updated and ideally fit inside the database's working-set memory.

2. Compound Indexes & the ESR Rule

A compound index covers multiple fields in a strict left-to-right order, e.g., { status: 1, createdAt: -1, totalCents: 1 }. Thanks to the leftmost prefix rule, that single index supports queries on (status), (status, createdAt), and (status, createdAt, totalCents), but cannot efficiently serve queries filtering solely on totalCents.

To order fields in a compound index for MongoDB or SQL, follow the ESR Rule:

  • E — Equality first: Exact-match filters (status: 'paid', tenantId: 't_1') narrow the index slice immediately.
  • S — Sort second: Ordering fields (createdAt: -1) let the database read results pre-sorted directly from the index without an expensive in-memory sort!
  • R — Range last: Inequality/range filters (totalCents: { $gte: 5000 }, $gt, $lt) appear last so they do not break the pre-sorted index order.

3. Query Execution and Explain Plans

Always verify assumptions with .explain('executionStats') in MongoDB or EXPLAIN ANALYZE in PostgreSQL. Focus on three numbers:

  • Stage Type: Look for IXSCAN (Index Scan) or Index Scan rather than COLLSCAN / Seq Scan, and avoid blocking SORT stages on large sets.
  • Examined-to-Returned Ratio: Compare totalDocsExamined and totalKeysExamined against nReturned. Examining 50,000 documents to return 20 means your index is missing or poorly ordered; an ideal covered/targeted index examines ~20 keys and 20 (or 0) documents.
  • Execution Time: executionTimeMillis under realistic data volumes.

4. Avoiding Inefficient Queries & N+1 Problems

  • Unanchored Regexes: Leading-wildcard patterns like /laptop/i or SQL LIKE '%laptop%' cannot use standard B-Tree indexes. Use prefix anchored regexes (/^laptop/), full-text indexes, or dedicated search engines.
  • Negations & Computed Predicates: $ne, $nin, and wrapping SQL columns in functions (WHERE LOWER(email) = ... without an expression index) bypass standard index lookups.
  • N+1 Queries: Batch child lookups using $in, SQL JOIN, or aggregation $lookup instead of querying inside loops.

5. Transactions and Atomic Operations

When updating a single document (e.g., deducting product stock or incrementing a counter), prefer atomic conditional updates (findOneAndUpdate with { _id, stock: { $gte: qty } } and $inc) over multi-document transactions—they acquire minimal locks and perform far faster.

When an invariant spans multiple records or collections/tables (such as debiting Account A and crediting Account B, or inserting an Order plus an Outbox Event), wrap both operations in an ACID transaction (session.withTransaction() in MongoDB replica sets or BEGIN ... COMMIT in SQL). Keep transactions tiny—never execute slow third-party HTTP calls inside an open database transaction!

6. Database Connection Pooling

Establishing a fresh database connection requires TCP handshake, TLS negotiation, and authentication. Drivers maintain a reusable connection pool (`maxPoolSize`, `minPoolSize`, `waitQueueTimeoutMS`). Size pools thoughtfully across replicas (instances * maxPoolSize < dbLimit) and fail fast with queue timeouts rather than letting requests pile up indefinitely.

7. Schema and Data Modeling Trade-Offs

In document databases like MongoDB, decide between embedding (storing line items inside an Order document—single fast read, atomic single-doc updates) and referencing (storing separate documents linked by ID—prevents unbounded array growth past MongoDB's 16 MB document limit and avoids duplicating rapidly changing shared entities). Rule of thumb: embed bounded data read together; reference unbounded growth (comments, logs, thousands of events) or shared entities.

8. MongoDB Aggregation Pipeline

Aggregation pipelines process data directly inside MongoDB across stages ($match, $sort, $limit, $group, $lookup, $project). Always place $match and $sort as the earliest stages so MongoDB can leverage B-Tree indexes before documents flow into memory-heavy $group or $lookup stages.

9. Relational Database Concepts & When SQL Wins

Relational databases (PostgreSQL, MySQL) enforce strict schemas, foreign-key referential integrity, normalized tables, and mature multi-table JOIN query optimizers with rock-solid ACID guarantees. Choose SQL over MongoDB when your domain has highly interconnected many-to-many relationships, complex ad-hoc reporting joins, strict financial/ledger invariants, or schema rigor where preventing orphan records at the database engine level matters most.

10. Backups and Data Consistency Concepts

Indexes and replication protect against single-node hardware failure, not accidental DROP COLLECTION or buggy migration scripts (which replicate instantaneously to followers!). Production databases require automated encrypted backups, Point-in-Time Recovery (PITR) via oplog/WAL archives, periodic restore drills into staging (an untested backup is not a backup), and explicit write/read concerns (e.g., MongoDB w: 'majority') so acknowledged writes survive primary failover.

03. Mechanics

Query Optimization Inspection Cycle

  1. Identify Slow Queries: Enable database slow-query profiling (e.g., queries > 50–100ms) in staging/production logs.
  2. Run Execution Stats: Execute .explain('executionStats') or EXPLAIN ANALYZE to see exact scan type, keys examined, docs examined, and sort behavior.
  3. Align Index with ESR + Projection: Create a compound index matching Equality, Sort, and Range order, and project only needed columns.
  4. Re-Verify Ratio & Write Impact: Confirm totalDocsExamined drops close to nReturned and remove redundant overlapping indexes so writes remain fast.

import mongoose from 'mongoose';

const orderSchema = new mongoose.Schema(
  {
    tenantId: { type: mongoose.Schema.Types.ObjectId, required: true },
    customerId: { type: mongoose.Schema.Types.ObjectId, required: true },
    status: { type: String, enum: ['pending', 'paid', 'shipped', 'cancelled'], required: true },
    totalCents: { type: Number, required: true },
    createdAt: { type: Date, default: Date.now }
  },
  { versionKey: false }
);

orderSchema.index({ tenantId: 1, status: 1, createdAt: -1, totalCents: 1 });
orderSchema.index({ customerId: 1, createdAt: -1 });

export const OrderModel = mongoose.model('Order', orderSchema);

export async function connectDatabase() {
  await mongoose.connect(process.env.MONGO_URI, {
    maxPoolSize: 20,
    minPoolSize: 4,
    serverSelectionTimeoutMS: 5000,
    socketTimeoutMS: 15000
  });
}

Step 2: Optimize Aggregation Pipelines & Inspect Explain Stats

src/modules/orders/order.analytics.repository.js 
export async function getTopTenantOrders({ tenantId, status, minTotalCents, limit = 20 }) {
  return OrderModel.find({
    tenantId,
    status,
    totalCents: { $gte: minTotalCents }
  })
    .select('_id customerId totalCents status createdAt')
    .sort({ createdAt: -1 })
    .limit(limit)
    .lean();
}

export async function inspectOrderQueryPlan({ tenantId, status }) {
  const explanation = await OrderModel.find({ tenantId, status })
    .sort({ createdAt: -1 })
    .limit(20)
    .explain('executionStats');

  return {
    stage: explanation.queryPlanner?.winningPlan?.inputStage?.stage,
    nReturned: explanation.executionStats?.nReturned,
    totalKeysExamined: explanation.executionStats?.totalKeysExamined,
    totalDocsExamined: explanation.executionStats?.totalDocsExamined,
    executionTimeMillis: explanation.executionStats?.executionTimeMillis
  };
}

export async function getMonthlyRevenueByStatus(tenantId, sinceDate) {
  return OrderModel.aggregate([
    {
      $match: {
        tenantId,
        createdAt: { $gte: sinceDate }
      }
    },
    {
      $group: {
        _id: '$status',
        orderCount: { $sum: 1 },
        revenueCents: { $sum: '$totalCents' }
      }
    },
    {
      $project: {
        _id: 0,
        status: '$_id',
        orderCount: 1,
        revenueCents: 1
      }
    }
  ]);
}

Step 3: Multi-Document ACID Transaction for Balance Transfers

src/modules/wallet/transfer.service.js 
import mongoose from 'mongoose';
import { AppError } from '../../shared/errors/AppError.js';

export async function transferWalletFunds({ WalletModel, LedgerModel, fromId, toId, amountCents }) {
  if (!Number.isInteger(amountCents) || amountCents <= 0) {
    throw new AppError('Invalid transfer amount', 400, 'INVALID_AMOUNT');
  }

  const session = await mongoose.startSession();
  try {
    let ledgerEntry;
    await session.withTransaction(async () => {
      const debited = await WalletModel.findOneAndUpdate(
        { _id: fromId, balanceCents: { $gte: amountCents } },
        { $inc: { balanceCents: -amountCents } },
        { new: true, session }
      );
      if (!debited) {
        throw new AppError('Insufficient funds or missing source wallet', 409, 'INSUFFICIENT_FUNDS');
      }

      const credited = await WalletModel.findByIdAndUpdate(
        toId,
        { $inc: { balanceCents: amountCents } },
        { new: true, session }
      );
      if (!credited) {
        throw new AppError('Destination wallet not found', 404, 'WALLET_NOT_FOUND');
      }

      const [createdLedger] = await LedgerModel.create(
        [{ fromId, toId, amountCents, createdAt: new Date() }],
        { session }
      );
      ledgerEntry = createdLedger.toObject();
    });

    return ledgerEntry;
  } finally {
    await session.endSession();
  }
}

Key Code Sections Explained

  • { tenantId: 1, status: 1, createdAt: -1, totalCents: 1 }: Follows ESR strictly: Equality (tenantId, status), Sort (createdAt: -1), Range (totalCents).
  • Early $match in Aggregation: Filters documents via index before $group aggregates them, cutting memory and CPU dramatically.
  • session.withTransaction(): Automatically handles transient transaction retry semantics while ensuring debit, credit, and ledger write succeed or roll back atomically together.
  • finally { await session.endSession(); }: Guarantees database session resources never leak even when business errors abort the transaction.
06. Engineering Judgment

MongoDB vs. Relational SQL Trade-Offs

Factor MongoDB (Document Store) PostgreSQL (Relational SQL)
Data Shape Nested, polymorphic, evolving JSON-like documents Structured normalized tables + optional JSONB columns
Complex Multi-Entity Joins $lookup exists, though heavy multi-table joins are slower/clumsier Best-in-class join optimizer, foreign keys, CTEs, and window functions
Transactions & Integrity Atomic single-doc updates; multi-doc ACID on replica sets with higher overhead Native mature ACID transactions, foreign keys, check constraints
Best Fit Catalogs, CMS, event logs, user profiles with varying metadata Financial ledgers, billing, complex ERPs, inventory/booking relational systems
07. Production Readiness

Common Mistakes & Data Reliability Risks

Mistake 1: Over-Indexing Every Single Field

Performance risk: Adding 12 separate indexes per collection slows inserts/updates and bloats working-set RAM until active indexes fall back to disk.

Fix: Design consolidated compound indexes matching actual query shapes and audit unused indexes regularly.

Mistake 2: Unbounded Embedded Arrays

Reliability risk: Appending user activity events or comments into one parent document's array causes repeated document disk reallocation and eventually crashes at MongoDB's 16 MB BSON limit.

Fix: Keep embedded arrays strictly bounded; move unbounded items into a separate referenced collection.

Mistake 3: Holding Transactions Open During External Network Calls

Availability risk: Calling a 2-second Stripe or email API inside BEGIN ... COMMIT holds database row/document locks open, blocking concurrent writers and causing deadlocks.

Fix: Perform external calls outside transactions using state machines (pending → confirmed) or the Outbox pattern.

Mistake 4: Treating Replication as a Backup Strategy

Data loss risk: An accidental DELETE without a WHERE clause replicates to read replicas in milliseconds.

Fix: Maintain automated immutable snapshots, Point-in-Time Recovery logs, and regularly test full database restores.

10. Active Recall

Short-Answer Review Questions

A covered query occurs when every field in the filter, sort, and projection exists inside the index itself (e.g., excluding _id if not indexed). The database answers the entire query straight from the in-memory B-Tree index without reading full documents from disk (totalDocsExamined: 0).

Whenever the state change lives inside one document—such as deducting product inventory or appending a bounded sub-item conditionally with findOneAndUpdate. Single-document atomicity requires no distributed coordinator session and scales with far lower latency.

A MongoDB TTL index automatically deletes expired documents in the background once their timestamp passes the configured expiration window, preventing unbounded table growth without writing custom cleanup cron jobs.

Running $lookup before $limit(20) forces MongoDB to join related records for 50,000 rows only to discard 49,980 of them afterward. Sorting and limiting first ensures $lookup runs only on the 20 documents actually returned on the page.

maxPoolSize caps how many concurrent TCP database connections a single Node process opens, preventing DB overload. waitQueueTimeoutMS caps how long a query waits for a free pool slot before failing fast instead of queuing indefinitely under saturation.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: A pipeline runs $lookup on users first, then $sort: { createdAt: -1 }, then $match: { orgId }, then $limit: 20 on 200,000 orders. Reorder it cleanly and specify the exact compound index required.

Reference Solution 
export async function listRecentOrgOrders(OrderModel, orgId, limit = 20) {
  return OrderModel.aggregate([
    { $match: { orgId } },
    { $sort: { createdAt: -1 } },
    { $limit: limit },
    {
      $lookup: {
        from: 'users',
        localField: 'customerId',
        foreignField: '_id',
        pipeline: [{ $project: { name: 1, email: 1 } }],
        as: 'customer'
      }
    },
    { $unwind: { path: '$customer', preserveNullAndEmptyArrays: true } }
  ]);
}

Required Index: { orgId: 1, createdAt: -1 } allows the initial $match + $sort + $limit to read 20 documents straight from the index, running $lookup only 20 times with sub-pipeline field projection.

Problem: Write a PostgreSQL pool transaction helper in JavaScript using pg that atomically inserts an order and deducts inventory with parameterized queries (preventing SQL injection) and rolls back cleanly on any failure.

Reference Solution 
export async function createOrderSql(pool, { userId, productId, qty }) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    const stockRes = await client.query(
      'UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1 RETURNING price_cents',
      [qty, productId]
    );
    if (stockRes.rowCount === 0) {
      throw new Error('INSUFFICIENT_STOCK');
    }

    const totalCents = stockRes.rows[0].price_cents * qty;
    const orderRes = await client.query(
      'INSERT INTO orders (user_id, product_id, qty, total_cents) VALUES ($1, $2, $3, $4) RETURNING *',
      [userId, productId, qty, totalCents]
    );

    await client.query('COMMIT');
    return orderRes.rows[0];
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}

Problem: A SaaS company stores (1) customer billing subscriptions, invoices, and tax ledger lines, and (2) dynamic form submissions whose fields vary per tenant. Compare choosing PostgreSQL (with JSONB) vs. MongoDB vs. polyglot persistence.

Reference Architecture: PostgreSQL with relational tables for billing/invoices/ledger (leveraging foreign keys and strict ACID transactions) plus a JSONB column with GIN indexing for dynamic tenant form payloads handles both cleanly in a single operational database—avoiding cross-database distributed transactions unless scale later justifies splitting the form store.

12. Takeaways

Day 10 Revision Summary

  • Indexes & ESR: Order compound indexes by Equality, Sort, Range and verify IXSCAN + low examined ratios using explain plans.
  • Query hygiene: Avoid leading-wildcard regexes, unindexed negations, and N+1 loops; place $match and $limit early in aggregations.
  • Consistency: Favor atomic conditional updates for single records and short ACID transactions (with zero external network waits) for multi-record invariants.
  • Data modeling & SQL: Keep embedded document arrays bounded, size connection pools across scaled replicas, and pick PostgreSQL when strict relational integrity and complex joins dominate.
  • Backups: Pair replication with automated snapshots, Point-in-Time Recovery, and regular restore verification tests.
