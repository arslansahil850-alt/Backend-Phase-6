Day 15 Containers & Environments

Docker and Containerization

Backend services rarely run alone—they depend on exact Node.js versions, MongoDB or PostgreSQL, Redis, and native OS libraries. When developer laptops, CI runners, and cloud servers drift apart, deployments break mysteriously. Today you will learn how Docker images and containers package runtimes reproducibly, how to write optimized non-root Node.js Dockerfiles, and how Docker Compose orchestrates APIs, databases, networks, and persistent volumes cleanly.

Connection to Days 2, 12 & 14

Containers make horizontal scaling repeatable, ship JSON logs cleanly via stdout, and enforce non-root least privilege without baking secrets into images.

Core Principle

Build an immutable image once without secrets; inject environment configuration at container startup and keep durable database state in named volumes.

Practical Output

Author a layer-cached .dockerignore, multi-stage production Dockerfile, and compose.yaml linking Express, MongoDB, and Redis.

02. Deep Dive

Core Docker & Containerization Concepts

1. Containers vs. Images & Why Containerization Helps

A Docker Image is an immutable, read-only blueprint built from stacked filesystem layers (base OS/Node runtime + installed npm dependencies + application code). A Container is a live, isolated running instance created from that image with a thin writable scratch layer on top. Multiple containers can share identical underlying read-only image layers cleanly.

Unlike Virtual Machines (which boot a separate guest OS kernel per VM), containers share the host Linux kernel via namespaces and cgroups—starting in milliseconds and enabling identical behavior across laptops, Day 16 CI runners, and production clusters.

2. Dockerfile Structure & Layer Caching

Docker caches every instruction layer sequentially. If a step's files or command change, Docker invalidates that layer and every subsequent layer below it:

  • FROM node:22-alpine: Pinned major/minor slim base image (avoid floating :latest tags that break unexpectedly).
  • WORKDIR /app: Sets the working directory inside the container.
  • COPY package*.json ./ then RUN npm ci --omit=dev: Copying manifests before copying src/ lets Docker reuse the slow npm ci layer whenever application code changes without dependency edits!
  • COPY src ./src: Copies only needed runtime source files (filtered by .dockerignore).
  • USER node: Drops root privileges before running application code.
  • CMD ["node", "src/server.js"]: Uses JSON exec-form directly on node (PID 1) so SIGTERM signals reach your Day 2 graceful shutdown handler instead of being swallowed by /bin/sh or npm!

3. Environment Variables in Containers

Never put database passwords, JWT secrets, or API keys inside a Dockerfile via ENV or COPY .env .—anyone who pulls or inspects the image layers (`docker history`) can extract them! Always inject runtime configuration when launching containers (`docker run --env-file .env.local`, Compose `env_file:`, or cloud secret managers).

4. Docker Compose, Networking & Persistent Volumes

Real backends rarely consist of one container. Docker Compose defines your multi-service stack declaratively in compose.yaml:

  • Internal DNS Networking: Compose creates an isolated bridge network where containers reach each other by service name! Inside the api container, localhost means the API container itself—reach MongoDB at mongodb://mongo:27017/app and Redis at redis://redis:6379.
  • Healthchecks & depends_on: Waiting merely for container start does not mean PostgreSQL or MongoDB is ready to accept connections. Use healthcheck probes paired with depends_on: { condition: service_healthy }.
  • Persistent Volumes: Container filesystems are ephemeral—running docker compose down destroys the writable layer. Mount a named volume (mongo_data:/data/db) so database files survive container restarts and image upgrades.

5. Development vs. Production Container Concerns

In local development, you mount your local source folder with a bind mount (./src:/app/src) and run node --watch for instant edits without rebuilding images. In production, never mount host source folders—build an immutable minimal image using multi-stage builds (stripping TypeScript compilers, test runners, and build tools), run as non-root USER node, attach explicit memory/CPU limits and HEALTHCHECK, and store zero secrets inside the image.

03. Mechanics

Container Build & Multi-Service Startup Flow

  1. Build Context Filtering: Docker reads .dockerignore first, skipping node_modules, .git, and .env so host binaries and secrets never enter the build context.
  2. Layered Build: Docker executes npm ci on cached package-lock.json, copies src/, switches to non-root node user, and produces a tagged immutable image.
  3. Compose Network & Health Ordering: docker compose up creates a private bridge network, boots mongo and redis attached to named volumes, waits for their healthchecks to pass, and then launches api with injected runtime environment variables.

Step 2: Write a Clean, Non-Root Production Dockerfile

Dockerfile 
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production

COPY --from=deps /app/node_modules ./node_modules
COPY package.json ./
COPY src ./src

RUN chown -R node:node /app
USER node

EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD node -e "fetch('http://127.0.0.1:3000/health').then((r) => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"

CMD ["node", "src/server.js"]

Step 3: Multi-Service Local Stack in compose.yaml

compose.yaml 
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
      PORT: 3000
      MONGO_URI: mongodb://mongo:27017/phase6_dev
      REDIS_URL: redis://redis:6379
      JWT_ACCESS_SECRET: ${JWT_ACCESS_SECRET}
    depends_on:
      mongo:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped

  mongo:
    image: mongo:7
    ports:
      - "27017:27017"
    volumes:
      - mongo_data:/data/db
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

volumes:
  mongo_data:
  redis_data:

Key Code Sections Explained

  • Multi-Stage Build (AS deps → AS runner): Keeps build caches and potential native compile tools out of the final production image.
  • USER node: Runs the Express process with unprivileged permissions instead of Linux root, limiting container-escape blast radius.
  • CMD ["node", "src/server.js"]: Running node directly as PID 1 ensures docker stop's SIGTERM triggers Express graceful shutdown cleanly.
  • condition: service_healthy: Prevents the API from crashing on boot while MongoDB or Redis is still initializing.
06. Engineering Judgment

Development vs. Production Container Concerns

Aspect Development Container Production Container
Code Delivery Bind mount (./src:/app/src) + node --watch Baked immutable image artifact built in CI
Dependencies Includes devDependencies (linters, test tools) npm ci --omit=dev only; smallest attack surface
Databases Local Compose containers with named volumes Managed cloud DBs or hardened stateful clusters with automated backups
Secrets Local untracked .env file passed via Compose Injected at runtime by orchestrator / cloud secret manager
07. Production Readiness

Common Container Mistakes & Security Pitfalls

Mistake 1: Copying .env or Secrets into the Image

Security leak: COPY . . without .dockerignore embeds local secrets into immutable image layers pushed to registries.

Fix: Ignore .env* in .dockerignore and supply environment variables strictly at container runtime.

Mistake 2: Connecting to localhost for Sibling DB Containers

Connection failure: Inside the api container, mongodb://localhost:27017 connects to the api container's own loopback interface, failing with ECONNREFUSED.

Fix: Use the Compose service name as hostname (mongodb://mongo:27017/...).

Mistake 3: Using Shell-Form CMD npm start

Graceful shutdown failure: Spawning sh -c "npm start" puts the shell at PID 1, which often fails to forward SIGTERM to Node.js, causing abrupt 10-second kills during deploys.

Fix: Use exec-form CMD ["node", "src/server.js"].

Mistake 4: Omitting Named Volumes on Database Containers

Data loss: Re-creating a database container without a volume wipes every database record immediately.

Fix: Always mount persistent named volumes at the DB data path (/data/db for MongoDB, /var/lib/postgresql/data for PostgreSQL).

08. Hands-On Practice

Practical Containerization Task

Milestone Task: Containerize an Express + Database Stack

Take a small Express API that exposes /health, /ready, and a simple CRUD resource backed by MongoDB or PostgreSQL + Redis:

  1. Create .dockerignore excluding node_modules, .git, and .env*.
  2. Write a multi-stage Dockerfile using pinned node:22-alpine, layer-cached npm ci --omit=dev, non-root USER node, and exec-form CMD.
  3. Create a compose.yaml linking api, database (with named volume + healthcheck), and redis, verifying /ready returns 200 after docker compose up --build.
  4. Verify persistence by creating a record, running docker compose down (without -v), running docker compose up again, and confirming the record remains intact.

10. Active Recall

Short-Answer Review Questions

Virtual Machines emulate full hardware and boot an entire guest OS kernel per VM. Containers share the host Linux kernel directly using OS isolation primitives (namespaces and cgroups), starting in milliseconds with minimal memory overhead.

docker compose down stops and removes containers and the bridge network while preserving named volumes (keeping your database records safe). Adding the -v flag also deletes named volumes, wiping local database data permanently.

The :latest tag changes silently over time—meaning a rebuild months later might suddenly pull a brand-new major Node.js version with breaking changes. Pinning versions keeps builds predictable and reproducible.

In local development, bind mounts sync file edits into the running container immediately for fast iteration. In production, containers need self-contained immutable artifacts built in CI so every scaled replica across any cloud host runs the exact tested code.

Native add-ons compile binary .node files targeting the host OS and C standard library (e.g., Windows/macOS or glibc Ubuntu vs musl Alpine). Listing node_modules in .dockerignore ensures npm ci installs/builds binaries specifically matching the container OS.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: Review this broken Dockerfile: FROM node:latest / WORKDIR /app / COPY . . / RUN npm install / CMD npm start (with no .dockerignore). Identify 4 flaws and explain the fix.

Reference Fixes: (1) Pin base image (node:22-alpine); (2) Add .dockerignore excluding node_modules, .git, .env*; (3) Copy package*.json and run npm ci --omit=dev before copying src/ for layer caching and deterministic installs; (4) Switch to non-root USER node and exec-form CMD ["node", "src/server.js"] for security and clean SIGTERM graceful shutdown.

Problem: Write a PostgreSQL 16 Compose service named postgres using persistent volume pg_data, environment placeholders, and a working pg_isready healthcheck.

Reference Solution (compose.yaml snippet) 
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app_dev
      POSTGRES_USER: ${PG_USER}
      POSTGRES_PASSWORD: ${PG_PASSWORD}
    ports:
      - "5432:5432"
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${PG_USER} -d app_dev"]
      interval: 10s
      timeout: 5s
      retries: 5

Problem: Using Day 5's worker architecture, explain how one single built Dockerfile image can run both the Express api service and the BullMQ worker service cleanly in compose.yaml.

Reference Architecture: Build one shared image containing both src/server.js and src/workerMain.js. In compose.yaml, define service api (exposing port 3000, default CMD ["node", "src/server.js"]) and service worker (using the exact same image, zero exposed HTTP ports, overriding command: ["node", "src/workerMain.js"]), both sharing Redis/DB env configuration and scaling independently.

12. Takeaways

Day 15 Revision Summary

  • Images vs. Containers: Read-only layered blueprints produce fast, isolated runtime containers sharing the host kernel.
  • Dockerfile best practices: Use pinned slim bases, .dockerignore, ordered package*.json + npm ci --omit=dev caching, non-root USER node, and exec-form CMD.
  • Runtime secrets: Never bake .env or credentials inside images; inject config at startup.
  • Docker Compose: Connect services via internal DNS service names, gate startup with service_healthy, and persist DBs with named volumes.
