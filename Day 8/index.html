Day 08 Identity, Access & Security

Advanced Authentication and Authorization

Checking whether a JWT is valid only proves who sent a request—it says nothing about whether that user is allowed to edit an invoice, delete another customer's project, or impersonate an administrator. Today you will learn production-grade access and refresh token lifecycles, secure token storage, RBAC, fine-grained permissions, resource ownership enforcement, session revocation, and multi-factor authentication design.

Connection to Days 2 & 4

Stateless short-lived access tokens work across scaled nodes, while Redis-backed session/revocation stores keep logout and compromised-token invalidation immediate.

Core Principle

Authentication establishes identity (401); authorization verifies permissions and resource ownership on every protected action (403).

Practical Output

Extend an Express API with rotating refresh tokens, role-to-permission mapping, and service-level resource ownership policies.

02. Deep Dive

Core Authentication & Authorization Concepts

1. Authentication vs. Authorization

  • Authentication (AuthN — "Who are you?"): Verifying identity via password, OAuth provider, passkey, or cryptographic token. Missing or invalid credentials return 401 Unauthorized.
  • Authorization (AuthZ — "What can you do?"): Checking whether an authenticated principal has permission to perform a specific action on a specific target resource. Insufficient privileges return 403 Forbidden.

2. Access and Refresh Token Lifecycle

Issuing a single 30-day JWT with no server check means stolen tokens stay valid for a month. Production token systems split responsibilities into two tokens:

  • Access Token: Short-lived (5–15 minutes), signed JWT carrying minimal claims (sub user ID, roles or scope, jti token ID, exp, iss, aud). Sent on API requests.
  • Refresh Token: Longer-lived (7–30 days), high-entropy opaque random string (or signed token) stored hashed on the server. Used solely at POST /auth/refresh to mint a fresh access token.

Refresh Token Rotation: Every time a refresh token is used, the server invalidates the old refresh token and issues a brand-new refresh + access pair. If an already-used refresh token is presented again (indicating either a stolen token was replayed or a victim's token was stolen), the server detects reuse and revokes the entire session family immediately.

3. Secure Token Handling (Browser vs. Server)

Understanding browser-side versus server-side boundaries is vital:

  • Browser Storage Risk: Any JavaScript running on your page—including a third-party script or XSS payload—can read localStorage or sessionStorage. Keep refresh tokens out of localStorage; deliver refresh tokens in HttpOnly, Secure, SameSite=Lax (or Strict) cookies scoped to /api/auth so browser scripts cannot read them.
  • CSRF Awareness with Cookies: Because browsers automatically attach cookies on cross-site requests, cookie-authenticated mutating endpoints need SameSite attributes, origin/CORS validation, or explicit CSRF token defenses.
  • JWT Payload Transparency: Standard signed JWTs (JWS) are Base64URL-encoded, not encrypted. Anyone holding a JWT can decode its claims—never store passwords, secrets, or sensitive personal data inside JWT claims.

4. Role-Based Access Control (RBAC)

RBAC assigns users coarse roles such as customer, support, editor, or admin. Route middleware verifies whether the caller's role is permitted. RBAC is intuitive, fast to understand, and maps naturally to organization hierarchies.

5. Permission-Based Authorization

Hardcoding role names directly inside 80 route handlers (if (user.role === 'editor' || user.role === 'manager' || user.role === 'admin')) becomes brittle when requirements change ("Let support agents view invoices, but not issue refunds").

Permission-based authorization checks explicit action capabilities—such as invoices:read, invoices:refund, or users:manage—while maintaining a centralized role-to-permissions map (or database permission table). Handlers ask "Can the user perform invoices:refund?" rather than hardcoding every role name everywhere.

6. Resource Ownership Checks (Preventing IDOR / BOLA)

Checking that a user has the orders:read permission is not enough if GET /api/orders/9876 lets User A read User B's order simply by guessing ID 9876. This flaw is called Broken Object Level Authorization (BOLA) or Insecure Direct Object Reference (IDOR).

Always enforce ownership or tenant scope inside your service/repository queries (e.g., querying { _id: orderId, ownerId: user.id } or checking resource.ownerId === user.id || hasPermission(user, 'orders:read:any')).

7. Session Management, Revocation & Logout Strategies

A user expects clicking "Log out" or "Reset Password" to actually stop access:

  • Logout (Single Device): Delete or mark the current refresh token family revoked in Redis/DB and clear the HttpOnly refresh cookie.
  • Global Revocation (Password Change / Compromise): Increment a tokenVersion integer on the user record (cached briefly in Redis) or store a revokedBefore timestamp. Middleware rejects any access token issued prior to that version/timestamp, and revokes all active refresh families.
  • Immediate Access-Token Denylist: For high-security endpoints, store revoked access token jti IDs in Redis with a TTL matching the remaining token lifetime (e.g., 10 minutes), keeping the Redis set tiny.

8. Multi-Factor Authentication (MFA) Concepts

Passwords alone fail against credential stuffing and phishing. MFA combines independent factors: something you know (password), something you have (authenticator app TOTP code or hardware WebAuthn/passkey), or something you are (biometrics verifying a device passkey).

Architecturally, when a user passes primary password login and has MFA enabled, do not issue a full API access token yet. Issue a short-lived, single-purpose mfa_pending token valid only for POST /auth/mfa/verify, rate-limit attempts strictly, hash single-use recovery backup codes just like passwords, and upgrade to full access/refresh tokens only after factor 2 succeeds.

9. Common Authentication Design Mistakes

  • Verifying JWTs without pinning algorithms: ['HS256'] (or ['RS256']), issuer, and audience.
  • Storing raw unhashed refresh tokens in the database (if DB read access leaks, attackers can mint unlimited access tokens).
  • Trusting client-supplied req.body.userId or req.body.role instead of reading verified req.user.id.
  • Returning different error messages ("User not found" vs "Wrong password") that allow email enumeration.
03. Mechanics

End-to-End Request Authorization & Refresh Flow

  1. Authenticate Principal: Middleware extracts Bearer access token, verifies cryptographic signature, pinned algorithm, expiry, and optional revocation version, setting req.user (or failing with 401).
  2. Authorize Capability: Route policy checks whether req.user holds the required permission (e.g., documents:update), failing with 403 if absent.
  3. Authorize Specific Resource: Service fetches target resource and verifies doc.ownerId === req.user.id (or elevated documents:update:any permission), failing with 403 or safe 404 if unauthorized.
  4. Silent Token Refresh: When the short access token expires, the client calls POST /auth/refresh (sending the HttpOnly cookie); server verifies the SHA-256 token hash, rotates to a new token pair, and rejects replayed tokens by revoking the whole family.

05. Step-by-Step Implementation

Implementing RBAC, Permissions, Ownership & Token Rotation

Notice how clean separation from Day 1 lets us keep route middleware concise while enforcing resource ownership inside the service and policy layer.

Step 1: Role-to-Permission Catalog & Policy Helpers

src/modules/auth/permissions.js 
export const ROLE_PERMISSIONS = Object.freeze({
  viewer: ['documents:read'],
  editor: ['documents:read', 'documents:create', 'documents:edit'],
  moderator: ['documents:read', 'documents:read:any', 'documents:edit:any'],
  admin: [
    'documents:read',
    'documents:read:any',
    'documents:create',
    'documents:edit',
    'documents:edit:any',
    'documents:delete:any',
    'users:manage'
  ]
});

export function getPermissionsForRoles(roles = []) {
  const permissionSet = new Set();
  for (const role of roles) {
    const list = ROLE_PERMISSIONS[role] || [];
    for (const perm of list) {
      permissionSet.add(perm);
    }
  }
  return permissionSet;
}

export function canAccessDocument(user, doc, action) {
  const perms = getPermissionsForRoles(user.roles);
  if (perms.has(`documents:${action}:any`)) {
    return true;
  }
  if (!perms.has(`documents:${action}`)) {
    return false;
  }
  const isOwner = String(doc.ownerId) === String(user.id);
  const isCollaborator = Array.isArray(doc.collaboratorIds)
    && doc.collaboratorIds.some((id) => String(id) === String(user.id));

  return action === 'read' ? isOwner || isCollaborator : isOwner;
}

Step 2: Authentication & Permission Middleware

src/shared/middlewares/authMiddleware.js 
import jwt from 'jsonwebtoken';
import { AppError } from '../errors/AppError.js';
import { getPermissionsForRoles } from '../../modules/auth/permissions.js';

export function createAuthenticateMiddleware({ userSessionCache }) {
  return async (req, res, next) => {
    const authHeader = req.get('Authorization') || '';
    if (!authHeader.startsWith('Bearer ')) {
      return next(new AppError('Authentication required', 401, 'AUTH_REQUIRED'));
    }

    const token = authHeader.slice(7).trim();
    try {
      const payload = jwt.verify(token, process.env.JWT_ACCESS_SECRET, {
        algorithms: ['HS256'],
        issuer: process.env.JWT_ISSUER,
        audience: process.env.JWT_AUDIENCE
      });

      const currentVersion = await userSessionCache.getTokenVersion(payload.sub);
      if (currentVersion !== null && payload.tv !== currentVersion) {
        return next(new AppError('Session revoked', 401, 'TOKEN_REVOKED'));
      }

      req.user = {
        id: payload.sub,
        roles: Array.isArray(payload.roles) ? payload.roles : [],
        jti: payload.jti
      };
      next();
    } catch (err) {
      next(new AppError('Invalid or expired access token', 401, 'INVALID_TOKEN'));
    }
  };
}

export function requirePermission(requiredPermission) {
  return (req, res, next) => {
    if (!req.user) {
      return next(new AppError('Authentication required', 401, 'AUTH_REQUIRED'));
    }
    const permissions = getPermissionsForRoles(req.user.roles);
    if (!permissions.has(requiredPermission)) {
      return next(new AppError('Insufficient permissions', 403, 'FORBIDDEN'));
    }
    next();
  };
}

Step 3: Refresh Token Rotation with Reuse Detection & Logout

src/modules/auth/tokenRotation.service.js 
import crypto from 'node:crypto';
import jwt from 'jsonwebtoken';
import { AppError } from '../../shared/errors/AppError.js';

function hashToken(rawToken) {
  return crypto.createHash('sha256').update(rawToken).digest('hex');
}

export class TokenRotationService {
  constructor({ refreshTokenRepo, userRepo }) {
    this.refreshTokenRepo = refreshTokenRepo;
    this.userRepo = userRepo;
  }

  signAccessToken(user) {
    return jwt.sign(
      {
        roles: user.roles,
        tv: user.tokenVersion
      },
      process.env.JWT_ACCESS_SECRET,
      {
        algorithm: 'HS256',
        subject: String(user._id),
        jwtid: crypto.randomUUID(),
        issuer: process.env.JWT_ISSUER,
        audience: process.env.JWT_AUDIENCE,
        expiresIn: '10m'
      }
    );
  }

  async issueInitialSession(user) {
    const rawRefresh = crypto.randomBytes(48).toString('base64url');
    const familyId = crypto.randomUUID();
    const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000);

    await this.refreshTokenRepo.create({
      userId: user._id,
      familyId,
      tokenHash: hashToken(rawRefresh),
      usedAt: null,
      revokedAt: null,
      expiresAt
    });

    return {
      accessToken: this.signAccessToken(user),
      refreshToken: rawRefresh
    };
  }

  async rotateRefreshToken(rawRefresh) {
    const tokenHash = hashToken(rawRefresh);
    const record = await this.refreshTokenRepo.findByHash(tokenHash);

    if (!record || record.revokedAt || record.expiresAt <= new Date()) {
      throw new AppError('Refresh session invalid', 401, 'INVALID_REFRESH');
    }

    if (record.usedAt !== null) {
      await this.refreshTokenRepo.revokeFamily(record.familyId);
      throw new AppError('Token reuse detected; session revoked', 401, 'REFRESH_REUSE');
    }

    const markedUsed = await this.refreshTokenRepo.markUsedAtomically(record._id);
    if (!markedUsed) {
      await this.refreshTokenRepo.revokeFamily(record.familyId);
      throw new AppError('Concurrent refresh conflict', 401, 'REFRESH_CONFLICT');
    }

    const user = await this.userRepo.findById(record.userId);
    if (!user || user.disabled) {
      await this.refreshTokenRepo.revokeFamily(record.familyId);
      throw new AppError('Account unavailable', 401, 'ACCOUNT_DISABLED');
    }

    const nextRawRefresh = crypto.randomBytes(48).toString('base64url');
    await this.refreshTokenRepo.create({
      userId: user._id,
      familyId: record.familyId,
      tokenHash: hashToken(nextRawRefresh),
      usedAt: null,
      revokedAt: null,
      expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)
    });

    return {
      accessToken: this.signAccessToken(user),
      refreshToken: nextRawRefresh
    };
  }

  async logoutSession(rawRefresh) {
    if (!rawRefresh) {
      return;
    }
    const record = await this.refreshTokenRepo.findByHash(hashToken(rawRefresh));
    if (record) {
      await this.refreshTokenRepo.revokeFamily(record.familyId);
    }
  }
}

Step 4: Enforcing Ownership Inside the Document Service

src/modules/documents/document.service.js 
import { AppError } from '../../shared/errors/AppError.js';
import { canAccessDocument } from '../auth/permissions.js';

export class DocumentService {
  constructor(documentRepo) {
    this.documentRepo = documentRepo;
  }

  async updateDocument({ documentId, updates, actor }) {
    const doc = await this.documentRepo.findById(documentId);
    if (!doc) {
      throw new AppError('Document not found', 404, 'DOC_NOT_FOUND');
    }

    if (!canAccessDocument(actor, doc, 'edit')) {
      throw new AppError('You do not have permission to edit this document', 403, 'FORBIDDEN');
    }

    return this.documentRepo.updateById(documentId, updates);
  }
}

Key Code Sections Explained

  • Pinned algorithms: ['HS256'], issuer, audience: Prevents algorithm-downgrade or cross-service token confusion attacks.
  • SHA-256 Hashing of Refresh Tokens: Unlike passwords (which need slow salted bcrypt/argon2), high-entropy 48-byte random tokens cannot be brute-forced, so fast SHA-256 hashing enables instant indexed lookups without exposing usable tokens if database backups leak.
  • markUsedAtomically + revokeFamily: Ensures two simultaneous refresh attempts cannot both mint tokens, and immediately kills the entire login session family if a stolen refresh token is replayed.
  • canAccessDocument Policy: Keeps ownership rules centralized and unit-testable instead of scattering if (doc.ownerId === req.user.id) across controllers.
06. Engineering Judgment

Session Strategies & Authorization Trade-Offs

Strategy Revocation Speed DB / Redis Reads per Request Best Fit
Stateful Redis Session + Cookie Instant (delete Redis key) 1 fast Redis lookup per request Browser-first web apps and dashboards where instant server control is top priority
Short JWT (10m) + Rotated Refresh Token Up to 10m natural expiry (or instant with tv/jti check) Zero DB hits for pure stateless JWT; 1 Redis check if tv enforced APIs serving web, mobile, and third-party/service consumers across multiple nodes

RBAC vs. Permission-Based vs. Ownership

Most mature APIs combine all three: assign roles to users for administration simplicity, map roles to granular permissions checked by route middleware, and verify resource ownership (or tenant ID) inside the service layer.

Browser vs. Server Responsibility Note

When setting refresh tokens in an HttpOnly; Secure; SameSite=Lax cookie, browser JavaScript cannot read the cookie—the browser attaches it automatically to POST /api/auth/refresh when fetch(..., { credentials: 'include' }) is used, keeping refresh credentials safe from XSS scripts.

07. Production Readiness

Common Authentication & Access Control Mistakes

Mistake 1: Route-Only Role Middleware Without Resource Ownership Checks

Vulnerability (IDOR / BOLA): Checking requirePermission('invoices:read') ensures the caller is a logged-in customer, but without verifying invoice.customerId === req.user.id they can download every other customer's invoices.

Fix: Enforce ownership/tenant filters in repositories and service policies on every single-record lookup.

Mistake 2: Issuing Long-Lived Unrevocable JWTs

Security risk: A 7-day access token with no version or denylist check continues working for days after a user clicks "Log out" or an employee is terminated.

Fix: Keep access token TTL short (5–15 minutes), support refresh revocation, and check tokenVersion via fast Redis cache on sensitive actions.

Mistake 3: Forgetting to Hash Refresh Tokens & MFA Recovery Codes

Security risk: Plaintext refresh tokens in a database give anyone with read access to backups immediate impersonation power.

Fix: Store SHA-256 digests of refresh tokens and bcrypt/argon2 hashes of passwords and recovery codes.

Mistake 4: Failing Open on Missing Secrets or Role Checks

Security risk: Writing jwt.verify(token, process.env.SECRET || 'dev-secret') allows attackers to forge tokens using the public fallback string if an env variable is omitted!

Fix: Fail startup immediately if required auth secrets are missing from environment variables, and default all authorization checks to deny.

10. Active Recall

Short-Answer Review Questions

401 Unauthorized means the caller is unauthenticated (missing, expired, or invalid credentials). 403 Forbidden means the caller's identity was successfully verified, but they lack the required role, permission, or resource ownership to perform that action.

Human-chosen passwords have low entropy and must be protected against offline brute-force cracking using slow, memory-hard salted hashing (Argon2id/bcrypt). Random 256-bit+ refresh tokens already have huge cryptographic entropy that cannot be guessed by brute force, so fast SHA-256 hashing prevents plaintext leakage while allowing fast database index lookups.

Differentiating "Email not found" from "Incorrect password" lets attackers run automated email-enumeration lists to discover which customers hold accounts on your platform, enabling targeted phishing and credential stuffing.

Because browsers automatically send cookies on cross-origin requests, you must guard against Cross-Site Request Forgery (CSRF) by setting SameSite=Lax or Strict, restricting CORS origins strictly, and validating CSRF tokens or custom headers on state-changing routes.

Backup recovery codes bypass the second factor if a user loses their authenticator device. They must be generated with high randomness, displayed once to the user, stored hashed on the server, and marked consumed immediately after single use.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: A route updates a user's note via PATCH /api/notes/:id using const { userId, role, content } = req.body; and runs NoteModel.findByIdAndUpdate(req.params.id, { content }). Identify the flaws and write the secure controller + service logic.

Reference Solution 
export async function updateNoteService({ noteId, content, actor, noteRepo }) {
  const updated = await noteRepo.updateOwnedById(noteId, actor.id, { content });
  if (!updated) {
    const exists = await noteRepo.existsById(noteId);
    if (!exists) {
      throw new AppError('Note not found', 404, 'NOTE_NOT_FOUND');
    }
    throw new AppError('Forbidden', 403, 'FORBIDDEN');
  }
  return updated;
}

Fixes: Never read userId or role from req.body; always take verified req.user from auth middleware and bind ownership atomically in the query.

Problem: Write an Express middleware requireMfaPendingToken that verifies a short-lived pre-auth JWT carrying purpose: 'mfa_challenge' and rejects normal API access tokens or tokens with wrong purpose.

Reference Solution 
import jwt from 'jsonwebtoken';
import { AppError } from '../shared/errors/AppError.js';

export function requireMfaPendingToken(req, res, next) {
  const token = req.body?.mfaToken;
  if (!token) {
    return next(new AppError('MFA challenge token required', 401, 'MFA_TOKEN_REQUIRED'));
  }

  try {
    const payload = jwt.verify(token, process.env.JWT_MFA_SECRET, {
      algorithms: ['HS256'],
      issuer: process.env.JWT_ISSUER
    });
    if (payload.purpose !== 'mfa_challenge') {
      return next(new AppError('Invalid token purpose', 401, 'INVALID_MFA_TOKEN'));
    }
    req.mfaUserId = payload.sub;
    next();
  } catch (err) {
    next(new AppError('Expired or invalid MFA challenge token', 401, 'INVALID_MFA_TOKEN'));
  }
}

Problem: A single user belongs to Organization A as an admin and Organization B as a viewer. Why does putting a single global roles: ['admin'] claim inside the user's JWT fail, and how should you design tenant-scoped authorization?

Reference Architecture: Never apply a user's role in Org A across Org B. Either (1) resolve membership and role for the requested orgId (from route param/header) against a cached org_memberships lookup in Redis/DB per request, or (2) issue organization-scoped access tokens carrying { sub, orgId, orgRoles } and enforce resource.orgId === req.orgContext.orgId on every repository query.

12. Takeaways

Day 8 Revision Summary

  • AuthN vs AuthZ: Identity verification returns 401 on failure; capability and ownership checks return 403.
  • Token Lifecycles: Short-lived access tokens + rotated SHA-256-hashed refresh tokens in HttpOnly cookies limit theft windows and detect replay.
  • RBAC + Permissions + Ownership: Map roles to granular permissions and always enforce object-level ownership/tenant boundaries to prevent IDOR.
  • Revocation & MFA: Use refresh family revocation, tokenVersion caches, and isolated pre-auth tokens before MFA completion.
  • Defensive Hygiene: Pin JWT algorithms/issuers/audiences, fail closed on missing env secrets, and never store secrets inside JWT payloads.
