Day 12 Observability & Reliability

Logging, Monitoring, and Error Tracking

When an API slows down or fails in production across multiple containers, SSHing into a server to read console.log is impossible. Today you will learn how structured JSON logs, correlation IDs, metrics dashboards, error-tracking aggregators, health and readiness probes, symptom-based alerting, and strict data redaction turn opaque production incidents into fast, diagnosable fixes.

Connection to Days 2, 5 & 6

Correlation IDs let you trace one user action across scaled HTTP servers, Redis caches, background workers, and async message queues.

Core Principle

Metrics tell you that something is wrong (5xx spike), error trackers group what crashed, and structured logs explain why for a specific request—without leaking secrets.

Practical Output

Instrument an Express API with a Pino structured logger, AsyncLocalStorage request IDs, sensitive-field redaction, /health + /ready endpoints, and centralized error handling.

02. Deep Dive

Core Observability & Error Tracking Concepts

1. Logging vs. Monitoring vs. Error Tracking

  • Logging: Discrete, timestamped records of events (e.g., an HTTP request completing, an order failing validation, or a worker retrying a job). Great for deep per-request debugging.
  • Monitoring (Metrics & Dashboards): Aggregated numeric time-series measurements collected over intervals—requests/sec, error rate %, p95/p99 latency, CPU, memory, and queue depth. Great for spotting trends and triggering alerts cheaply.
  • Error Tracking: Dedicated tools (such as Sentry or Bugsnag) that capture unhandled exceptions, group identical stack traces by fingerprint, track affected user counts, tag the deployed release version, and record breadcrumbs leading up to the crash.

2. Structured Logging & Log Levels

Plain strings like console.log('Order failed for user ' + id) are painful to filter across millions of log lines. Structured logging (using fast Node libraries like pino or winston) writes single-line JSON objects to stdout: {"level":"error","time":...,"requestId":"req_8f2","userId":"u_42","durationMs":142,"msg":"Payment timeout"}. Log collectors (Grafana Loki, Datadog, CloudWatch, ELK) index these JSON properties automatically for instant querying.

Use log levels intentionally and control verbosity via LOG_LEVEL environment variable:

  • debug: Verbose diagnostic details enabled only in local dev or brief staging debugging.
  • info: Normal operational milestones (server started, request completed, job finished).
  • warn: Recoverable anomalies (cache connection dropped and fell back to DB, retry attempt 2, client rate-limited).
  • error / fatal: Failed operations requiring investigation (500 unhandled exception, DB connection pool down, startup secret missing).

3. Request IDs and Correlation IDs

When 500 requests execute concurrently, log lines interleave randomly. Assigning a unique Request ID (reading incoming X-Request-Id or generating a UUID, and echoing it back in the response header) lets you filter all log entries belonging to one HTTP call.

A Correlation ID spans an entire multi-hop workflow—attached when the API receives a request, passed inside background job metadata (Day 5), event envelopes (Day 6), and outbound HTTP headers so you can trace a failure from HTTP API to worker to broker. Node's built-in AsyncLocalStorage keeps context accessible inside deep services without manually passing req everywhere!

4. Centralized Error Handling

Every Express app needs one final four-argument error middleware (err, req, res, next) plus process-level listeners for unhandledRejection and uncaughtException. Distinguish operational errors (expected 4xx validation, not-found, conflict errors logged at info/warn) from unexpected programmer/system crashes (5xx logged at error with full stack trace + requestId, returning only a safe generic message plus requestId to the caller).

5. Health Checks and Readiness Checks

  • Liveness (GET /health): Fast, zero-dependency check confirming the Node.js process is alive and the event loop is responsive. Never check external APIs or heavy DB queries inside liveness—if Redis blips for 2 seconds, you do not want Kubernetes killing and restarting every API container simultaneously!
  • Readiness (GET /ready): Verifies critical direct dependencies (lightweight SELECT 1 / Mongo ping + Redis ping with tight 1–2s timeouts). Returns 200 when ready to receive load-balancer traffic, or 503 Service Unavailable during startup/shutdown or dependency loss.

6. Metrics, Dashboards & Alerting Principles

Effective backend dashboards monitor the Four Golden Signals (and the RED method for APIs):

  • Traffic / Rate: Requests per second by route and status class.
  • Errors: Rate of HTTP 5xx responses and failed background jobs.
  • Duration (Latency): p50, p95, and p99 response times.
  • Saturation: Event-loop delay, heap memory usage, CPU %, DB connection pool utilization, and queue depth.

Alerting discipline: Page engineers only on actionable, user-impacting symptoms (e.g., 5xx error rate > 2% for 5 minutes, p99 latency > 1.5s sustained, readiness probe failing)—not single isolated warnings or 404 typos that create alert fatigue.

7. Avoiding Sensitive Data in Logs

Logs are frequently shipped to third-party SaaS platforms and readable by wider engineering/support teams. Never log plaintext passwords, JWTs, API keys, session cookies, credit card numbers, or unmasked secrets. Configure automatic logger redaction paths (redact) and avoid dumping raw req.headers or raw req.body blindly into logs.

03. Mechanics

Request-to-Observability Telemetry Flow

  1. Context Initialization: Edge middleware extracts or creates requestId and correlationId, opens an AsyncLocalStorage store, sets the response header X-Request-Id, and records start time.
  2. Automatic Context Logging: Services and repositories call the logger anywhere; Pino's mixin reads AsyncLocalStorage automatically and redacts sensitive keys before writing JSON to stdout.
  3. Metrics & Error Capture: On response finish, metrics increment status counters and latency histograms. Any unexpected error bubbles to centralized error middleware, logs internally with full stack + requestId, reports to error tracking, and replies safely to the client.

05. Step-by-Step Implementation

Adding Structured Logging, Health Checks & Error Handling

Step 1: Structured Redacting Logger + AsyncLocalStorage Context

src/shared/observability/logger.js 
import { AsyncLocalStorage } from 'node:async_hooks';
import pino from 'pino';

export const requestContext = new AsyncLocalStorage();

export const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  base: {
    service: process.env.SERVICE_NAME || 'api-server',
    env: process.env.NODE_ENV || 'development'
  },
  redact: {
    paths: [
      'req.headers.authorization',
      'req.headers.cookie',
      'password',
      'token',
      'refreshToken',
      'secret',
      '*.password',
      '*.token',
      '*.secret'
    ],
    censor: '[REDACTED]'
  },
  mixin() {
    const store = requestContext.getStore();
    return store
      ? { requestId: store.requestId, correlationId: store.correlationId, userId: store.userId }
      : {};
  }
});

Step 2: Request/Correlation ID & HTTP Access Logging Middleware

src/shared/middlewares/requestTelemetry.js 
import crypto from 'node:crypto';
import { performance } from 'node:perf_hooks';
import { logger, requestContext } from '../observability/logger.js';

export function requestTelemetryMiddleware(req, res, next) {
  const requestId = req.get('X-Request-Id') || crypto.randomUUID();
  const correlationId = req.get('X-Correlation-Id') || requestId;

  req.id = requestId;
  req.correlationId = correlationId;
  res.setHeader('X-Request-Id', requestId);
  res.setHeader('X-Correlation-Id', correlationId);

  const start = performance.now();
  const store = { requestId, correlationId, userId: null };

  requestContext.run(store, () => {
    res.on('finish', () => {
      if (req.user?.id) {
        store.userId = req.user.id;
      }
      const durationMs = Number((performance.now() - start).toFixed(2));
      const logLevel = res.statusCode >= 500 ? 'error' : res.statusCode >= 400 ? 'warn' : 'info';
      logger[logLevel](
        {
          method: req.method,
          path: req.route ? req.baseUrl + req.route.path : req.path,
          statusCode: res.statusCode,
          durationMs
        },
        'http_request_completed'
      );
    });
    next();
  });
}

Step 3: Health, Readiness & Centralized Error Handler

src/shared/routes/healthAndErrors.js 
import express from 'express';
import { logger } from '../observability/logger.js';

function withTimeout(promise, ms, label) {
  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error(`${label}_TIMEOUT`)), ms);
  });
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer));
}

export function createHealthRouter({ checkDb, checkRedis }) {
  const router = express.Router();

  router.get('/health', (req, res) => {
    res.status(200).json({
      status: 'ok',
      uptimeSeconds: Math.round(process.uptime())
    });
  });

  router.get('/ready', async (req, res) => {
    const checks = {};
    let allHealthy = true;

    try {
      await withTimeout(checkDb(), 1500, 'DB');
      checks.database = 'up';
    } catch (err) {
      checks.database = 'down';
      allHealthy = false;
    }

    try {
      await withTimeout(checkRedis(), 1000, 'REDIS');
      checks.redis = 'up';
    } catch (err) {
      checks.redis = 'down';
      allHealthy = false;
    }

    res.status(allHealthy ? 200 : 503).json({
      status: allHealthy ? 'ready' : 'not_ready',
      checks
    });
  });

  return router;
}

export function createErrorHandler({ errorTracker }) {
  return (err, req, res, next) => {
    const isOperational = Boolean(err && err.isOperational);
    const statusCode = isOperational ? err.statusCode : 500;

    if (!isOperational || statusCode >= 500) {
      logger.error({ err, path: req.path, method: req.method }, 'unhandled_server_error');
      if (errorTracker) {
        errorTracker.captureException(err, { requestId: req.id, path: req.path });
      }
    } else {
      logger.warn({ code: err.code, statusCode, message: err.message }, 'operational_client_error');
    }

    res.status(statusCode).json({
      status: 'error',
      code: isOperational ? err.code : 'INTERNAL_ERROR',
      message: isOperational ? err.message : 'An unexpected error occurred',
      requestId: req.id || null
    });
  };
}

Key Code Sections Explained

  • redact: { paths: [...], censor: '[REDACTED]' }: Strips sensitive credentials automatically before JSON hits stdout.
  • AsyncLocalStorage Mixin: Attaches requestId and correlationId to deep service/repository logs automatically without altering function signatures.
  • Normalized Route Path (req.route ? req.baseUrl + req.route.path : req.path): Prevents high-cardinality unique IDs (/users/123, /users/124) from exploding metric/log grouping dashboards; groups under /users/:id instead!
  • withTimeout on /ready: Ensures a hung database socket does not stall the readiness endpoint for 30 seconds while the load balancer waits.
06. Engineering Judgment

Telemetry Roles & Alerting Comparison

Pillar Primary Question Answered Storage Cost / Volume Example Action
Metrics "Is the system degraded right now, and how much?" Very low (numeric counters/histograms) Alert when 5xx error ratio exceeds 2% or p99 > 1.2s
Error Tracking "Which exception occurred, how often, and in which release?" Low-moderate (grouped by stack fingerprint) Link crash spike to commit deployed 10 minutes ago

07. Production Readiness

Common Observability & Security Mistakes

Mistake 1: Logging Entire req.body or req.headers

Security breach: Logging login/signup bodies or full headers saves plaintext passwords, Bearer JWTs, and session cookies into centralized log archives.

Fix: Log explicit safe fields only and enforce logger-level redaction paths on sensitive keys.

Mistake 2: Using /ready Logic Inside /health Liveness

Cascading outage: Restarting every Node container whenever a database briefly stalls amplifies recovery delays and drops healthy cached traffic.

Fix: Keep /health strictly process-local; check DB/Redis inside /ready.

Mistake 3: Using Unbounded Dynamic URLs in Metric Labels

Memory crash: Recording metrics tagged by raw req.originalUrl (including /orders/uuid-1, /orders/uuid-2) creates millions of unique time-series keys that crash Prometheus/Node memory.

Fix: Always label metrics by matched Express route template (/orders/:id).

Mistake 4: Paging On-Call Engineers on Every Single Error

Alert fatigue: Sending Slack/PagerDuty alerts for every 404 or transient retry trains engineers to ignore real outages.

Fix: Alert on sustained symptom thresholds (error-rate burn, queue depth growth, readiness outage) and log 4xx client errors as info/warn.

10. Active Recall

Short-Answer Review Questions

A requestId identifies a single HTTP call to one service instance. A correlationId identifies an entire end-to-end business workflow across multiple services, background jobs, and message queue consumers.

Containers have ephemeral filesystems and scale dynamically. Writing structured JSON to stdout follows the Twelve-Factor App principle so platform log collectors (Docker, Kubernetes, cloud agents) ship logs reliably without filling container disks.

Operational errors are expected runtime failures (bad user input, missing record, conflict) handled cleanly with safe 4xx messages. Programmer/unexpected errors (null dereference, driver crash) return generic 500 responses while logging full stack traces and triggering alerts.

If the database is silently dropping packets, a default TCP timeout can hang for 30+ seconds—longer than the load balancer's probe timeout. Bounding checks with Promise.race returns an explicit 503 JSON response promptly.

Alert fatigue happens when teams trigger noisy notifications for non-actionable events (single transient retries, normal 404s, short CPU blips), leading engineers to mute channels. Avoid it by alerting only on sustained user-impacting SLO symptoms that require human action.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: A developer logs console.log('Login attempt:', req.body, req.headers); inside auth middleware and loses request IDs inside OrderService. Fix both issues.

Reference Solution 
export function logAuthAttempt(email) {
  const maskedEmail = email.replace(/(^.).*(@.*$)/, '$1***$2');
  logger.info({ maskedEmail }, 'auth_login_attempted');
}

Fixes: Never dump raw req.body or req.headers; log masked identifiers via Pino configured with redact and AsyncLocalStorage mixin so requestId appears automatically in every service log.

Problem: From Day 5, when Express enqueues a BullMQ job and a worker runs it later, AsyncLocalStorage from the HTTP request is gone. Show how to pass and restore correlationId in the worker.

Reference Solution 
export async function enqueueWithContext(queue, name, payload) {
  const ctx = requestContext.getStore();
  return queue.add(name, {
    ...payload,
    correlationId: ctx?.correlationId || crypto.randomUUID()
  });
}

export async function runJobWithContext(job, handler) {
  const store = {
    requestId: `job:${job.id}`,
    correlationId: job.data.correlationId || `job:${job.id}`,
    userId: job.data.userId || null
  };
  return requestContext.run(store, () => handler(job));
}

Problem: Outline what happens when an unhandledRejection fires outside Express middleware in Node.js, and list the top 5 panels you would put on an Express API production dashboard.

Reference Architecture: Attach a process-level process.on('unhandledRejection', ...) handler that logs a fatal error, flushes the error tracker, triggers graceful shutdown (draining HTTP server with a short timeout), and exits cleanly so the container orchestrator restarts a healthy process rather than running in a corrupted state. Top 5 dashboard panels: (1) Request Rate by route/status, (2) 5xx Error % Rate, (3) p50/p95/p99 Latency, (4) Event-Loop Delay & Heap Usage, and (5) DB Pool Wait Time + Queue Waiting Depth.

12. Takeaways

Day 12 Revision Summary

  • Three pillars: Metrics show system health trends, error trackers group crashes, and structured JSON logs explain individual failures.
  • Context propagation: AsyncLocalStorage and X-Correlation-Id link HTTP, worker, and broker logs cleanly.
  • Probes: Keep /health lightweight for process liveness and /ready timeout-bounded for dependency readiness.
  • Centralized errors: Return safe operational errors + requestId to clients while logging full 5xx details internally.
  • Zero secret leaks: Redact auth headers, cookies, tokens, and passwords automatically inside the logger.
