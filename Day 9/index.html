Day 09 API Contracts & Evolution

Advanced API Design and Versioning

An API is a long-term contract with web apps, mobile builds that users rarely update, and third-party partners. Renaming a single JSON field or changing an error format casually can break production clients overnight. Today you will learn how to design predictable REST contracts, filter and paginate safely, handle versioning and deprecation without duplicating business logic, document APIs with OpenAPI/Swagger, and evaluate when GraphQL makes sense.

Connection to Days 1 & 3

Layered DTO mappers let v1 and v2 controllers share one core service layer, while clamped pagination protects server memory and database latency.

Core Principle

Additive changes preserve backward compatibility; breaking contract changes belong behind explicit versioned adapters with clear deprecation timelines.

Practical Output

Implement versioned Express endpoints with allowlisted filtering/sorting/pagination, deprecation headers, and an OpenAPI specification.

02. Deep Dive

Core API Design & Versioning Concepts

1. REST API Design Principles

  • Resource-Oriented Nouns: Model endpoints around plural nouns (/api/v1/orders, /api/v1/orders/:id) rather than RPC verbs like /getAllOrders or /deleteOrderById. Use HTTP methods (GET, POST, PUT, PATCH, DELETE) for actions.
  • Action Sub-Resources When Needed: For state transitions that do not map cleanly to a field edit, use explicit sub-resources such as POST /api/v1/orders/:id/cancellations or POST /api/v1/invoices/:id/send.
  • Predictable Naming & Formats: Use consistent casing (camelCase JSON keys), UTC ISO-8601 timestamps (2026-11-15T09:15:00Z), and integer minor units for money (totalCents) or explicit currency objects.

2. API Versioning Strategies

  • URI Path Versioning (/api/v1/products, /api/v2/products): Most explicit, trivial to route, inspect in logs, bookmark, and cache in CDNs. Slightly violates strict "URI identifies a single timeless resource" purism, yet remains the industry favorite for public and mobile APIs.
  • Header Versioning (Accept: application/vnd.arslan.v2+json or API-Version: 2026-11-01): Keeps URLs clean; popular in date-versioned developer platforms (like Stripe). Requires configuring CDN/proxy Vary headers carefully and is harder to test casually in a browser bar.
  • Query Parameter Versioning (/api/products?version=2): Easy to default, though awkward with caching rules and mixes routing versions with filter parameters.

3. Consistent Response Formats

Every endpoint across an API should share a predictable top-level structure—for example:

  • Single resource: { "data": { ... }, "meta": { "requestId": "..." } }
  • Paginated collection: { "data": [ ... ], "pagination": { "limit": 20, "nextCursor": "...", "hasMore": true } }

Consistency eliminates special-case client parsing logic (e.g., one endpoint returning a bare array [...] while another returns { items: [...] }).

4. Filtering, Sorting, and Pagination

Allowing clients to pass arbitrary query keys directly into database queries is dangerous and slow. Production APIs strictly parse and allowlist query options:

  • Filtering: Explicitly whitelist filterable fields (category, status, minPriceCents, maxPriceCents) and coerce types cleanly (rejecting non-object values or Mongo operators like $ne).
  • Sorting: Map client sort tokens (e.g., ?sort=-priceCents,createdAt) only against an explicit allowlist of indexed fields so clients cannot sort on huge unindexed text blobs or internal columns.
  • Pagination: Combine strict limit clamping (e.g., 1–50) with cursor pagination for feeds/logs or offset pagination for bounded admin tables.

5. Idempotent Operations

An operation is idempotent if executing it multiple times produces the same server state as executing it once. By HTTP specification, GET, HEAD, PUT (full replacement), and DELETE are expected to be idempotent, whereas POST is non-idempotent by default.

For critical POST endpoints (charges, orders, transfers) where network retries happen, support an Idempotency-Key request header backed by shared Redis/database state (as implemented in Day 2) so duplicate retries safely return the original response.

6. Error Status Codes and Error Formats

Never return 200 OK with { "success": false }! Use accurate HTTP status codes paired with a consistent structured body (inspired by RFC 9457 Problem Details):

  • 400 Bad Request / 422 Unprocessable Entity: Malformed syntax or domain/field validation failures (include per-field details).
  • 401 Unauthorized: Missing/expired/invalid authentication.
  • 403 Forbidden: Authenticated, but lacks permission/ownership.
  • 404 Not Found: Resource does not exist (or masked for unauthorized tenants).
  • 409 Conflict: Duplicate unique email/slug, state conflict, or version mismatch.
  • 429 Too Many Requests: Rate limit exceeded (include Retry-After header).
  • 500 Internal Server Error / 503 Service Unavailable: Unexpected crash or dependency outage without leaking internal stack traces.

7. API Documentation with OpenAPI / Swagger

OpenAPI (formerly Swagger) is a language-agnostic YAML or JSON specification describing your endpoints, parameters, request/response schemas, authentication schemes, and error payloads. Serving interactive Swagger UI (swagger-ui-express) or Redoc lets frontend/mobile developers explore and test contracts directly, and enables automated client SDK generation and contract validation.

8. Backward Compatibility & API Deprecation

Know the boundary between safe and breaking changes:

  • Safe (Backward-Compatible): Adding a new endpoint, adding an optional request property, or adding a new response field (assuming clients ignore unknown fields).
  • Breaking (Requires New Version): Removing or renaming a JSON field, changing a field's type (string to number or object), changing URL paths, adding a new required request field, or changing error codes clients branch on.

When deprecating an older version (v1), emit standard Deprecation: true and Sunset: Wed, 30 Jun 2027 23:59:59 GMT HTTP headers plus a Link header pointing to migration docs, monitor usage metrics per version, and only sunset v1 after traffic drops or migration deadlines expire.

9. GraphQL Overview & When It Is Useful

GraphQL exposes a single typed schema endpoint (typically POST /graphql) where clients declare the exact fields and nested relationships they need in one query—solving over-fetching (downloading 40 fields when a mobile card needs 3) and under-fetching (making 5 sequential REST calls to assemble one screen).

However, GraphQL brings real backend trade-offs: standard HTTP/CDN URL caching no longer works out of the box for POST queries, deeply nested queries risk N+1 database explosions (requiring tools like DataLoader batching) and query-complexity DoS attacks, and file uploads/rate limiting require extra tooling. Use GraphQL when multiple clients need flexible views over richly connected data; stick to REST for straightforward resource APIs, heavy HTTP caching, webhooks, and public simplicity.

03. Mechanics

How Versioned Endpoints Share Core Services Cleanly

  1. Versioned Route Entry: Express mounts separate routers at /api/v1 and /api/v2, attaching deprecation/sunset headers to v1 responses automatically.
  2. Query Sanitization & Allowlisting: Middleware/parser converts raw req.query strings into typed, bounded filter, sort, and pagination objects.
  3. Shared Domain Service: Both v1 and v2 controllers call the same ProductService so business rules, caching, and validations never drift apart.
  4. Versioned DTO Presentation: Each controller maps the domain object into its version-specific response shape (for example, v1 keeps legacy flat price field while v2 returns structured pricing: { amountCents, currency }).

05. Step-by-Step Implementation

Implementing a Versioned, Filtered & Documented Express API

Step 1: Safe Allowlisted Filtering, Sorting & Pagination Parser

src/shared/query/parseCatalogQuery.js 
const ALLOWED_SORT_FIELDS = {
  createdAt: 'createdAt',
  price: 'priceCents',
  title: 'title'
};

export function parseCatalogQuery(rawQuery = {}) {
  const limitRaw = Number.parseInt(rawQuery.limit, 10);
  const limit = Number.isInteger(limitRaw) ? Math.min(Math.max(limitRaw, 1), 50) : 20;

  const pageRaw = Number.parseInt(rawQuery.page, 10);
  const page = Number.isInteger(pageRaw) ? Math.max(pageRaw, 1) : 1;

  const filters = {};
  if (typeof rawQuery.category === 'string' && rawQuery.category.trim()) {
    filters.category = rawQuery.category.trim().toLowerCase();
  }

  const minPrice = Number.parseInt(rawQuery.minPriceCents, 10);
  const maxPrice = Number.parseInt(rawQuery.maxPriceCents, 10);
  if (Number.isInteger(minPrice) && minPrice >= 0) {
    filters.minPriceCents = minPrice;
  }
  if (Number.isInteger(maxPrice) && maxPrice >= 0) {
    filters.maxPriceCents = maxPrice;
  }

  const sortTokens = typeof rawQuery.sort === 'string' ? rawQuery.sort.split(',') : ['-createdAt'];
  const sort = {};
  for (const token of sortTokens) {
    const trimmed = token.trim();
    if (!trimmed) {
      continue;
    }
    const descending = trimmed.startsWith('-');
    const clientField = descending ? trimmed.slice(1) : trimmed;
    const dbField = ALLOWED_SORT_FIELDS[clientField];
    if (dbField) {
      sort[dbField] = descending ? -1 : 1;
    }
  }
  if (Object.keys(sort).length === 0) {
    sort.createdAt = -1;
  }

  return { page, limit, filters, sort };
}

Step 2: Deprecation Headers Middleware & Versioned Controllers

src/modules/products/product.versioned.routes.js 
import express from 'express';
import { parseCatalogQuery } from '../../shared/query/parseCatalogQuery.js';

export function deprecateVersion({ sunsetDate, migrationUrl }) {
  return (req, res, next) => {
    res.set('Deprecation', 'true');
    res.set('Sunset', sunsetDate);
    res.set('Link', `<${migrationUrl}>; rel="deprecation"`);
    next();
  };
}

function toV1Dto(product) {
  return {
    id: String(product._id),
    name: product.title,
    price: Number((product.priceCents / 100).toFixed(2)),
    category: product.category
  };
}

function toV2Dto(product) {
  return {
    id: String(product._id),
    title: product.title,
    category: product.category,
    pricing: {
      amountCents: product.priceCents,
      currency: product.currency || 'USD'
    },
    createdAt: product.createdAt
  };
}

export function createProductVersionedRouters(productService) {
  const v1Router = express.Router();
  v1Router.use(
    deprecateVersion({
      sunsetDate: 'Wed, 30 Jun 2027 23:59:59 GMT',
      migrationUrl: 'https://api.example.com/docs/v1-to-v2'
    })
  );

  v1Router.get('/', async (req, res, next) => {
    try {
      const options = parseCatalogQuery(req.query);
      const result = await productService.listProducts(options);
      res.status(200).json({
        data: result.items.map(toV1Dto),
        pagination: result.pagination
      });
    } catch (err) {
      next(err);
    }
  });

  const v2Router = express.Router();
  v2Router.get('/', async (req, res, next) => {
    try {
      const options = parseCatalogQuery(req.query);
      const result = await productService.listProducts(options);
      res.status(200).json({
        data: result.items.map(toV2Dto),
        pagination: result.pagination,
        meta: { apiVersion: 'v2' }
      });
    } catch (err) {
      next(err);
    }
  });

  return { v1Router, v2Router };
}

src/app.js — Mounting Versioned Routers & Swagger UI 
import fs from 'node:fs';
import express from 'express';
import yaml from 'js-yaml';
import swaggerUi from 'swagger-ui-express';

export function mountApiDocsAndVersions(app, { v1Router, v2Router }) {
  const openApiSpec = yaml.load(fs.readFileSync('./docs/openapi.yaml', 'utf8'));

  app.use('/api/docs', swaggerUi.serve, swaggerUi.setup(openApiSpec));
  app.use('/api/v1/products', v1Router);
  app.use('/api/v2/products', v2Router);
}

Key Code Sections Explained

  • Type Guard typeof rawQuery.category === 'string': In Express query parsing (qs), ?category[$ne]=books produces an object { $ne: 'books' }! Checking typeof === 'string' blocks NoSQL operator injection cleanly.
  • ALLOWED_SORT_FIELDS Lookup Map: Rejects unknown sort fields rather than passing user strings directly into .sort(), preventing performance abuse and hidden-field probing.
  • toV1Dto vs. toV2Dto: Renaming name to title and changing float price to integer pricing.amountCents would break v1 clients, so adapters translate the shared domain model cleanly for each version.
  • Deprecation & Sunset Headers: Standardized machine-readable signals let SDKs and partner monitoring detect deprecated endpoints automatically before removal.
06. Engineering Judgment

Versioning & REST vs. GraphQL Trade-Offs

Versioning Strategy Example Strengths Drawbacks
URI Path /api/v2/orders Explicit, easy CDN/proxy caching, simple Express routing and logs URL changes across major versions
Custom / Accept Header API-Version: 2026-11-01 Clean resource URLs, supports granular date-based rollouts Requires Vary header for caches; harder to test directly in browser bar
Query Parameter /api/orders?v=2 Easy optional default Mixes version routing with resource query filters; messier routing tables
Dimension REST + OpenAPI GraphQL
Over/Under-Fetching Fixed shapes per endpoint (unless sparse fieldsets added) Client picks exact fields and nested relations in 1 request
HTTP Caching Native GET URL + ETag / CDN caching POST /graphql bypasses standard HTTP caching unless persisted queries are used
Query Safety & N+1 Server controls fixed query shapes Needs DataLoader batching + depth/cost limiting to stop expensive nested queries
Versioning Explicit v1/v2 or date versions Schema evolution via additive fields + @deprecated field directives
07. Production Readiness

Common API Design Mistakes & Security Hygiene

Mistake 1: Forwarding Raw req.query Directly into Database Filters

Vulnerability: Calling Product.find(req.query) lets attackers pass query operators like ?price[$lt]=0 or filter on private unpublished fields like ?isDraft=true.

Fix: Parse, type-check, and allowlist every query parameter explicitly before building database filters.

Mistake 2: Breaking Backward Compatibility Inside an Existing Version

Reliability risk: Changing price from a number to "19.99" string or renaming id inside v1 crashes deployed iOS/Android clients that take weeks to update.

Fix: Keep changes inside v1 strictly additive; publish breaking structural changes under v2.

Mistake 3: Returning HTTP 200 OK for Errors

Observability & Client bug: Returning 200 with { ok: false } breaks HTTP client error interceptors, load-balancer error-rate dashboards, and CDN negative caching.

Fix: Return accurate 4xx/5xx codes with a consistent machine-readable error code and message body.

Mistake 4: Copy-Pasting Entire Services for v1 and v2

Maintenance risk: Duplicating business logic across v1/order.service.js and v2/order.service.js causes security fixes applied to v2 to be forgotten in v1.

Fix: Share one core service and map inputs/outputs in thin versioned controller/DTO adapters.

10. Active Recall

Short-Answer Review Questions

PUT performs a full replacement of a resource representation (omitted optional fields reset or become null, making it naturally idempotent). PATCH applies a partial modification containing only the fields the client wants to change.

URI path versions are immediately visible in server access logs, browser address bars, curl snippets, and OpenAPI docs, and CDNs/reverse proxies cache distinct URLs cleanly without needing special Vary header tuning.

Turning off v1 purely by calendar date while 20% of active mobile users or paying partners are still calling it causes immediate production outages. Tracking per-version metrics lets you reach out proactively to remaining callers and verify zero critical traffic before sunsetting.

DataLoader batches individual key lookups requested during a single event-loop tick (for example, 25 nested order.customer calls) into one combined database query (e.g., WHERE id IN (...)) and caches results per request.

Wrapping lists inside a JSON object lets you add pagination cursors, totals, or metadata keys later in a backward-compatible additive way—whereas changing a raw top-level array into an object is an instant breaking change for every client.

Problem: A route executes const docs = await Item.find(req.query).sort(req.query.sort); res.json(docs);. Identify 3 design/security bugs and write a safe replacement returning consistent paginated JSON.

Reference Solution 
export async function listItemsController(req, res, next) {
  try {
    const { page, limit, filters, sort } = parseCatalogQuery(req.query);
    const { items, total } = await itemService.list({ page, limit, filters, sort });
    res.status(200).json({
      data: items.map(toPublicItemDto),

      }

  } catch (err) {

Three bugs fixed: (1) Blocked NoSQL operator injection via allowlisted query parsing, (2) enforced bounded pagination + allowlisted sort fields, and (3) wrapped list inside a consistent extensible { data, pagination } envelope using a public DTO mapper.

Problem: Write an Express error-handling middleware that formats operational errors into a clean structured response containing type, title, status, code, detail, requestId, and optional errors array (for field validation errors) without leaking internal stack traces.

Reference Solution 
export function problemErrorHandler(err, req, res, next) {
  const isOperational = Boolean(err && err.isOperational);
  const status = isOperational ? err.statusCode : 500;
  const payload = {
    type: `https://api.example.com/errors/${isOperational ? err.code : 'INTERNAL_ERROR'}`,
    title: isOperational ? err.name : 'Internal Server Error',
    status,
    code: isOperational ? err.code : 'INTERNAL_ERROR',
    detail: isOperational ? err.message : 'An unexpected error occurred',
    requestId: req.id || null
  };

  if (isOperational && Array.isArray(err.details)) {
    payload.errors = err.details;
  }

  res.status(status).type('application/problem+json').json(payload);
}

Problem: A team is building two products: (A) a public payment/webhook developer platform used by external companies, and (B) an internal analytics dashboard aggregating 6 complex interrelated entities on one React screen. Which API paradigm/versioning fit each best?

Reference Architecture: Product (A) fits REST + OpenAPI with explicit URI or date-header versioning, strict idempotency keys, and signed webhooks because external developers value predictable contracts, HTTP status codes, and straightforward curl/SDK integration. Product (B) is a strong candidate for GraphQL (or a dedicated REST BFF aggregation endpoint) so the internal dashboard fetches exact nested slices in one trip while protecting resolvers with DataLoader and query-cost limits.

12. Takeaways

Day 9 Revision Summary

  • Predictable REST design uses plural resource nouns, standard HTTP status codes, consistent JSON envelopes, and idempotency keys on critical writes.
  • Safe querying strictly parses, type-checks, and allowlists filter and sort fields alongside clamped pagination.
  • Smart versioning keeps changes additive within a major version, isolates breaking DTO differences in thin adapters over shared services, and signals retirements via Deprecation/Sunset headers.
  • OpenAPI/Swagger documents contracts clearly for consumers and tooling.
  • GraphQL solves multi-resource over/under-fetching at the cost of extra caching, DataLoader N+1 management, and query complexity protection.
