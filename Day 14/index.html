Day 14 Defensive Security & Hardening

Rate Limiting and API Security

Any public API on the internet receives automated traffic within minutes: credential-stuffing bots, abusive scrapers, malformed payloads, and dependency scanners. Today you will learn defensive threat modeling, distributed rate limiting strategies, strict input validation, CORS and security headers, secrets and dependency hygiene, SQL/NoSQL injection and SSRF defenses, and how to conduct a structured security review.

Connection to Days 2, 4 & 8

Core Principle

Defense in depth: combine transport security, rate limits, schema validation, parameterized queries, least-privilege secrets, and safe error masking.

Practical Output

Review an exposed sample API for security flaws and implement Redis-backed rate limiting, Helmet/CORS hardening, Zod schema stripping, and an SSRF URL guard.

02. Deep Dive

Core API Security & Rate Limiting Concepts

1. Threat Modeling Fundamentals

Threat modeling asks four practical questions before shipping a feature: (1) What are we building? (data flows, APIs, external fetches, DBs); (2) What can go wrong? (using frameworks like STRIDE: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege); (3) What defenses mitigate each risk?; and (4) Did we verify those defenses with tests?

2. Rate Limiting Strategies & Brute-Force Protection

Rate limiting caps how many requests a caller can make within a window, returning 429 Too Many Requests along with standard Retry-After and RateLimit-* headers:

  • Fixed Window Counter: Increments a counter per key (e.g., rl:ip:1.2.3.4:170000) with TTL. Very fast, though allows up to 2x burst right across a window boundary.
  • Sliding Window (Log or Weighted Counter): Smooths boundary bursts by weighting the previous window or storing timestamps in a Redis Sorted Set (ZSET).
  • Token Bucket: Refills tokens at a steady rate up to a burst capacity—great when short legitimate bursts (loading a page) should succeed while sustained abuse gets throttled.
  • Brute-Force Protection: Apply stricter limits on POST /auth/login, POST /auth/mfa, and password resets—keyed by both IP and normalized account identifier (ip+email) so attackers using distributed IPs cannot brute-force one account, and one shared office IP does not lock out unrelated users.

3. Input Validation, Mass Assignment & Payload Bounds

Validate every incoming body, param, and query against strict schemas (e.g., Zod or Joi) that enforce types, string lengths, numeric bounds, and strip unknown keys. Passing raw req.body into User.create(req.body) allows mass assignment (a caller sending { "role": "admin", "isVerified": true }). Also cap JSON body sizes (`express.json({ limit: '100kb' })`) to block memory-exhaustion payloads.

4. CORS, Security Headers & Transport Security

  • Security Headers (helmet): Sets X-Content-Type-Options: nosniff, Strict-Transport-Security (HSTS), Referrer-Policy, and restrictive Content-Security-Policy headers, while removing X-Powered-By: Express.
  • Strict CORS: Browser Same-Origin Policy blocks cross-site JS reads by default. Never reflect arbitrary Origin headers or combine origin: '*' with credentials: true! Whitelist exact trusted frontend origins.
  • Cookies & HTTPS: Serve APIs strictly over HTTPS/TLS in production and flag auth cookies HttpOnly; Secure; SameSite=Lax (or Strict).

5. Secrets & Dependency Vulnerability Management

Keep API keys, JWT secrets, and DB URIs strictly in environment variables or secret managers—never hardcoded in source files or committed `.env` files. Validate required secrets at startup so apps fail fast if misconfigured. Lock dependency versions via `package-lock.json`, run `npm audit` in CI, and remove unused packages to shrink your supply-chain attack surface.

6. SQL / NoSQL Injection Prevention

  • SQL Injection Defense: Always use parameterized queries/prepared statements (pool.query('SELECT * FROM users WHERE email = $1', [email]))—never concatenate user strings into SQL templates!
  • NoSQL Injection Defense: When Express parses JSON or query strings, attackers can send objects like { "email": { "$ne": "" } }. Strict Zod schema validation rejecting non-string values where strings are expected completely prevents operator injection.

7. Server-Side Request Forgery (SSRF) Defenses

Whenever a backend fetches a user-supplied URL (for example, webhook delivery URLs, link-preview scrapers, or remote avatar imports), an attacker could submit internal URLs like http://127.0.0.1:6379 or cloud metadata endpoints like http://169.254.169.254/latest/meta-data/!

Defend against SSRF strictly: allow only https: (or explicit domain allowlists), resolve DNS to an IP address and reject all loopback, private RFC1918, link-local, and multicast IPs, disable automatic HTTP redirects (which could bounce from a public host to an internal IP), and enforce tight timeouts and response size caps.

03. Mechanics

Defense-in-Depth Request Ordering

  1. Network & Headers: Reverse proxy terminates TLS; Express applies trust proxy accurately, helmet() security headers, and strict cors() origin checks.
  2. Abuse & Size Gates: Redis rate limiter rejects abusive traffic early (429 + Retry-After) before expensive bcrypt hashing or DB queries run; express.json({ limit: '100kb' }) rejects oversized bodies.
  3. Schema & Auth Gates: Strict Zod schema parses and strips unknown keys; AuthN/AuthZ middleware verifies identity, permissions, and ownership.
  4. Safe Data & Error Boundary: Parameterized queries / typed filters interact with DB safely, and centralized error middleware suppresses internal stack traces in production responses.

05. Step-by-Step Implementation

Implementing Protective Middleware in Express

Step 1: Distributed Redis Sliding-Window Rate Limiter

src/shared/middlewares/rateLimiter.js 
import crypto from 'node:crypto';

export function createRedisSlidingLimiter({
  redisClient,
  prefix = 'rl',
  windowMs = 60000,
  maxRequests = 60,
  keyGenerator = (req) => req.ip
}) {
  return async (req, res, next) => {
    if (!redisClient || !redisClient.isReady) {
      return next();
    }

    const identifier = String(keyGenerator(req) || req.ip || 'unknown');
    const key = `${prefix}:${identifier}`;
    const now = Date.now();
    const windowStart = now - windowMs;
    const member = `${now}:${crypto.randomUUID()}`;

    try {
      const results = await redisClient
        .multi()
        .zRemRangeByScore(key, 0, windowStart)
        .zAdd(key, { score: now, value: member })
        .zCard(key)
        .pExpire(key, windowMs)
        .exec();

      const currentCount = Number(results[2] || 0);
      const remaining = Math.max(0, maxRequests - currentCount);

      res.setHeader('RateLimit-Limit', String(maxRequests));
      res.setHeader('RateLimit-Remaining', String(remaining));

      if (currentCount > maxRequests) {
        const retrySeconds = Math.ceil(windowMs / 1000);
        res.setHeader('Retry-After', String(retrySeconds));
        return res.status(429).json({
          status: 'error',
          code: 'RATE_LIMITED',
          message: 'Too many requests. Please try again later.'
        });
      }

      next();
    } catch (err) {
      next();
    }
  };
}

Step 2: Security Headers, Strict CORS & Strict Zod Schema Validation

src/shared/middlewares/securityBaseline.js 
import express from 'express';
import helmet from 'helmet';
import cors from 'cors';
import { z } from 'zod';
import { AppError } from '../errors/AppError.js';

export function applySecurityBaseline(app, allowedOrigins = []) {
  app.disable('x-powered-by');
  app.set('trust proxy', 1);

  app.use(
    helmet({
      contentSecurityPolicy: {
        directives: {
          defaultSrc: ["'self'"],
          objectSrc: ["'none'"],
          frameAncestors: ["'none'"]
        }
      },
      hsts: { maxAge: 31536000, includeSubDomains: true }
    })
  );

  app.use(
    cors({
      origin(origin, callback) {
        if (!origin || allowedOrigins.includes(origin)) {
          return callback(null, true);
        }
        callback(new AppError('Origin not allowed by CORS', 403, 'CORS_BLOCKED'));
      },
      credentials: true,
      methods: ['GET', 'POST', 'PATCH', 'PUT', 'DELETE'],
      allowedHeaders: ['Content-Type', 'Authorization', 'Idempotency-Key']
    })
  );

  app.use(express.json({ limit: '100kb' }));
}

export function validateBody(zodSchema) {
  return (req, res, next) => {
    const parsed = zodSchema.safeParse(req.body);
    if (!parsed.success) {
      return next(new AppError('Validation failed', 400, 'VALIDATION_ERROR'));
    }
    req.body = parsed.data;
    next();
  };
}

export const registerUserSchema = z
  .object({
    name: z.string().trim().min(2).max(80),

    password: z.string().min(12).max(128)

Step 3: Defensive SSRF Outbound URL Guard

src/shared/security/safeUrlGuard.js 
import dns from 'node:dns/promises';
import net from 'node:net';

function isPrivateOrReservedIpv4(ip) {
  const parts = ip.split('.').map(Number);
  if (parts.length !== 4 || parts.some((n) => !Number.isInteger(n) || n < 0 || n > 255)) {
    return true;
  }
  const [a, b] = parts;
  if (a === 0 || a === 10 || a === 127) return true;
  if (a === 169 && b === 254) return true;
  if (a === 172 && b >= 16 && b <= 31) return true;
  if (a === 192 && b === 168) return true;
  if (a === 100 && b >= 64 && b <= 127) return true;
  return false;
}

function isBlockedIp(ip) {
  if (net.isIPv4(ip)) {
    return isPrivateOrReservedIpv4(ip);
  }
  if (net.isIPv6(ip)) {
    const lower = ip.toLowerCase();
    return lower === '::1' || lower.startsWith('fc') || lower.startsWith('fd') || lower.startsWith('fe80');
  }
  return true;
}

export async function assertSafeOutboundHttpsUrl(rawUrl) {
  const parsed = new URL(rawUrl);
  if (parsed.protocol !== 'https:') {
    throw new Error('ONLY_HTTPS_ALLOWED');
  }
  if (parsed.username || parsed.password) {
    throw new Error('CREDENTIALS_IN_URL_FORBIDDEN');
  }

  const records = await dns.lookup(parsed.hostname, { all: true });
  if (!records.length) {
    throw new Error('DNS_RESOLUTION_FAILED');
  }
  for (const record of records) {
    if (isBlockedIp(record.address)) {
      throw new Error('RESTRICTED_DESTINATION_IP');
    }
  }
  return parsed.toString();
}

Key Code Sections Explained

  • Redis multi() Sliding Window: Executes range pruning, insertion, cardinality count, and expiry atomically across all scaled Express instances.
  • z.object(...).strict() + req.body = parsed.data: Rejects unexpected fields like role: 'admin' and ensures nested `$gt`/`$ne` injection objects fail type validation cleanly.
  • dns.lookup(..., { all: true }) in SSRF Guard: Checking hostname strings alone misses domains like local.example.com resolving to 127.0.0.1 or 169.254.169.254. Always inspect resolved IPs and pair with fetch(url, { redirect: 'error', signal: AbortSignal.timeout(3000) }).
06. Engineering Judgment

Rate Limiting Algorithm Comparison

Algorithm Memory Cost Burst Behavior Best Use Case
Fixed Window Counter Ultra-low (1 counter key) Allows up to 2x burst across window boundary Coarse high-volume API quota protection
Sliding Window (ZSET) Moderate (stores timestamp entries) Strict smooth enforcement with zero boundary spike Login/MFA brute-force protection, strict per-user quotas
Token Bucket Low (tokens + timestamp) Allows controlled short burst up to bucket size, refills smoothly Interactive UI/API traffic where bursts are normal
07. Security Review

Production API Security Review Checklist

  • All auth, login, MFA, and expensive routes enforce distributed Redis rate limiting keyed appropriately (IP + account identifier for login).
  • Every request body, query, and path param passes strict schema validation rejecting unknown keys and injection objects.
  • helmet(), strict CORS origin allowlists, bounded JSON body limits, and HttpOnly; Secure; SameSite cookies are configured.
  • Parameterized SQL queries and typed NoSQL queries are used everywhere; user uploads use magic-byte checks and safe isolation (Day 11).
  • Outbound URL fetches validate HTTPS + resolved non-private IPs + disabled redirects against SSRF.
  • Secrets reside only in env/secret stores, package-lock.json + npm audit run in CI, and production errors never leak stack traces.
08. Hands-On Practice

Practical Defensive Security Review Task

Milestone Task: Audit & Harden an Insecure Express API

Suppose you inherit an Express app containing: (1) app.use(cors({ origin: '*', credentials: true })), (2) User.create(req.body) on signup, (3) unlimited POST /auth/login, (4) raw fetch(req.body.webhookUrl), and (5) an error handler returning res.status(500).json({ error: err.stack }).

  1. Document all five vulnerabilities clearly using threat-modeling terms (Information Disclosure, Elevation of Privilege, SSRF, Brute-Force).
  2. Implement applySecurityBaseline with Helmet, explicit CORS allowlist, and 100 KB JSON body cap.
  3. Add Zod validation rejecting extra keys on signup, tiered Redis rate limiting on POST /auth/login, and assertSafeOutboundHttpsUrl on webhook saves/deliveries.

10. Active Recall

Short-Answer Review Questions

Each Node.js replica keeps an isolated counter in local RAM, multiplying the effective rate limit by the number of replicas and resetting all limits on every restart. Backing the limiter with shared Redis enforces one consistent limit cluster-wide.

HSTS tells browsers to remember that a domain must only be contacted over HTTPS for a configured duration (e.g., 1 year), preventing protocol-downgrade attacks and accidental plaintext HTTP requests.

An attacker-controlled public HTTPS server can pass initial DNS/IP validation, then reply with 302 Found pointing to http://169.254.169.254/... or http://127.0.0.1:8080. Disabling automatic redirects prevents HTTP clients from following unsafe redirects internally.

Fallback strings like process.env.JWT_SECRET || 'secret123' are often visible in codebases and let an API start silently in production with a trivial guessable signing key. Failing fast during startup catches configuration mistakes immediately before serving traffic.

Password hashing is intentionally CPU- and memory-intensive. Rejecting abusive request bursts at the Redis rate-limiting layer prevents attackers from exhausting worker threads and CPU via repeated login floods.

Problem: Write a Zod-based startup configuration loader loadEnvConfig(env) that requires strong minimum-length secrets (JWT_ACCESS_SECRET min 32 chars, MONGO_URI, ALLOWED_ORIGINS) and throws immediately if invalid.

Reference Solution 
import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  MONGO_URI: z.string().min(10),
  REDIS_URL: z.string().min(8),
  JWT_ACCESS_SECRET: z.string().min(32),
  ALLOWED_ORIGINS: z.string().transform((s) => s.split(',').map((o) => o.trim()).filter(Boolean))
});

export function loadEnvConfig(env = process.env) {
  return envSchema.parse(env);
}

Problem: Threat-model POST /auth/forgot-password and POST /auth/reset-password and specify 5 concrete defensive controls.

Reference Controls: (1) Strict rate limits per IP + per email to prevent email-bombing abuse; (2) Identical generic 200 response regardless of whether the email exists (anti-enumeration); (3) Cryptographically random 32+ byte reset token stored as a SHA-256 hash with short 15-minute TTL and single-use consumption; (4) Invalidate all active refresh token families and increment tokenVersion upon reset completion; (5) Log attempt metadata without logging the reset token itself.

12. Takeaways

Day 14 Revision Summary

  • Threat modeling identifies assets, trust boundaries, and prioritized mitigations before incidents occur.
  • Distributed rate limiting via Redis enforces consistent abuse and brute-force caps across horizontally scaled servers.
  • Input hygiene combines strict Zod validation, unknown-key stripping, bounded JSON limits, and parameterized queries.
  • Transport & browser headers pair Helmet, strict CORS allowlists, HTTPS, and HttpOnly; Secure; SameSite cookies.
  • SSRF & secrets safety validate resolved non-private IPs on outbound fetches, fail fast on missing env secrets, and keep error responses safe.
