Day 05 Async Processing & Workers

Background Jobs and Task Scheduling

Sending transactional emails, generating multi-page PDF invoices, resizing uploaded media, or syncing third-party webhooks inside an HTTP request forces users to wait on slow dependencies and risks load-balancer timeouts. Today you will learn how to offload heavy or unreliable tasks to persistent job queues and dedicated workers with safe retries, idempotency, scheduling, and status visibility.

Connection to Days 2 & 3

Offloading slow work keeps HTTP latency low, protects the Node.js event loop, and stops per-instance cron timers from duplicating work across scaled replicas.

Core Principle

An HTTP endpoint should validate intent, record durable state, enqueue a job, and return 202 Accepted quickly—letting workers handle slow execution reliably.

Practical Output

Move a slow report-generation workflow out of an Express route into a Redis-backed BullMQ queue and standalone worker with status tracking.

02. Deep Dive

Core Background Job Concepts

1. Synchronous vs. Asynchronous Work

In an HTTP request-response cycle, synchronous work (in the workflow sense) means the client waits on the open TCP connection until every step finishes—for example, validating input, inserting an order row, calling an email provider, and generating a PDF invoice.

Asynchronous background work decouples request acceptance from task completion: the API validates input, persists the record, pushes a job onto a persistent queue, and returns 202 Accepted in ~20ms. A separate worker picks up the job milliseconds later.

2. Why Background Jobs Are Useful

  • Faster User Experience: Users do not stare at a spinning button for 6 seconds while an SMTP server or PDF renderer works.
  • Resilience to Transient Outages: If an external email or webhook API goes down for 3 minutes, the queued job retries automatically instead of failing the user's signup or checkout.
  • Traffic Smoothing (Backpressure): If 2,000 users trigger video/report exports during a spike, the queue buffers them safely while 10 workers process jobs at a steady rate without crashing your database.
  • Independent Scaling: CPU-heavy workers can scale independently on high-CPU machines while lightweight web servers remain responsive.

3. Job Queues and Workers

A background job system has three components:

  • Producer (Express API / Service): Enqueues a lightweight job name and JSON payload (e.g., { reportId, userId }) into a durable backing store such as Redis (via BullMQ), PostgreSQL (via pg-boss), or MongoDB (via Agenda).
  • Queue Broker / Store: Persists waiting, delayed, active, and failed jobs so nothing vanishes if a Node.js process restarts.
  • Worker Process: A separate Node.js process pulling jobs from the queue, enforcing concurrency limits (for example, 5 concurrent jobs per worker), updating progress, and marking jobs complete or failed.

Important distinction: Calling sendEmail().catch(console.error) without await inside an Express route is not a reliable background job! If the container restarts or crashes 100ms later, that in-memory Promise vanishes permanently.

4. Scheduled and Recurring Tasks

Two scheduling patterns appear frequently in production:

  • Delayed Jobs: Run once after a specified delay—such as sending a trial-expiration reminder 48 hours after registration or canceling an unpaid reservation after 15 minutes.
  • Recurring (Cron) Jobs: Run on a schedule—such as generating daily digest emails at 08:00 UTC or purging expired tokens every hour.

Unlike naive setInterval or node-cron inside web servers (which execute N times if you run N web instances), queue-backed schedulers deduplicate repeatable job definitions in the central store so only one job fires per schedule interval.

5. Retry Strategies and Failure Handling

Retrying immediately in a tight loop punishes struggling external APIs and wastes worker capacity. Instead, configure exponential backoff with jitter: e.g., retry after 2s, 4s, 8s, 16s, plus slight randomness.

Equally important is separating transient errors (network timeout, HTTP 503, temporary lock) from permanent errors (malformed user email, deleted account, invalid schema). Permanent errors should fail immediately without wasting retries (in BullMQ, by throwing UnrecoverableError). Exhausted jobs stay in a failed state for inspection, alerting, or manual replay.

6. Idempotency Concepts

Most reliable job queues guarantee at-least-once delivery: if a worker finishes calling an external API and crashes right before acknowledging completion to Redis, the queue re-queues the job and another worker runs it again.

To prevent charging a customer twice or sending duplicate emails, job handlers must be idempotent:

  • Use deterministic job IDs (e.g., jobId: `welcome-email:${userId}`) so duplicate enqueue calls are ignored by the queue.
  • Track a durable processedAt or status transition in your primary database using conditional atomic updates (WHERE status = 'pending') before executing external side effects.

7. Job Status and Observability

Once work leaves the HTTP request, users and engineers need visibility. Expose a protected status endpoint (e.g., GET /api/reports/:id) backed by your domain record or job state, track job duration, failure counts, and queue depth (number of waiting jobs). A steadily climbing waiting queue means workers are falling behind incoming traffic or stuck on slow downstream calls.

8. Suitable Use Cases

Classic candidates include transactional emails, SMS/push delivery, PDF/CSV report exports, image/video processing, webhook fan-out to customer endpoints, search-index synchronization, and scheduled cleanup jobs.

03. Mechanics

End-to-End Background Job Execution Lifecycle

  1. Client Requests Slow Work: Client sends POST /api/reports requesting an annual sales export.
  2. API Validates & Persists Intent: Express checks authorization, creates a Report row with status: 'queued' in the database, and pushes { reportId, userId } into the queue with a deterministic jobId.
  3. Fast HTTP Response: Express immediately replies 202 Accepted with { reportId, statusUrl: '/api/reports/...' }.
  4. Worker Consumes & Updates Progress: A separate worker node picks up the job, transitions DB status to processing, queries data in batches, uploads the finished CSV/PDF to object storage, and sets status to ready.
  5. Failure & Recovery Path: If a transient error occurs, the queue reschedules the job into a delayed set according to exponential backoff until attempts are exhausted.

05. Step-by-Step Implementation

Moving Heavy Report Generation to a BullMQ Queue & Worker

Below is a practical refactoring using BullMQ (backed by Redis). Notice that the Express API process and the Worker process live in separate entrypoints so they can run and scale independently.

Step 1: Define the Queue & Default Retry Policy

src/queues/report.queue.js 
import { Queue } from 'bullmq';
import IORedis from 'ioredis';

export function createQueueConnection() {
  return new IORedis(process.env.REDIS_URL, {
    maxRetriesPerRequest: null
  });
}

export function createReportQueue(connection) {
  return new Queue('reports', {
    connection,
    defaultJobOptions: {
      attempts: 4,
      backoff: {
        type: 'exponential',
        delay: 2000
      },
      removeOnComplete: { age: 3600, count: 500 },
      removeOnFail: { age: 86400, count: 1000 }
    }
  });
}

Step 2: Enqueue Jobs from Express & Expose Safe Status

src/modules/reports/report.routes.js 
import express from 'express';

export function createReportRouter({ reportRepository, reportQueue }) {
  const router = express.Router();

  router.post('/', async (req, res, next) => {
    try {
      const report = await reportRepository.create({
        userId: req.user.id,
        rangeStart: req.body.rangeStart,
        rangeEnd: req.body.rangeEnd,
        status: 'queued'
      });

      const job = await reportQueue.add(
        'generate-monthly-report',
        { reportId: report._id, userId: req.user.id },
        { jobId: `report:${report._id}` }
      );

      res.status(202).json({
        status: 'accepted',
        data: {
          reportId: report._id,
          jobId: job.id,
          pollUrl: `/api/reports/${report._id}`
        }
      });
    } catch (err) {
      next(err);
    }
  });

  router.get('/:id', async (req, res, next) => {
    try {
      const report = await reportRepository.findOwnedById(req.params.id, req.user.id);
      if (!report) {
        return res.status(404).json({ error: 'Report not found' });
      }
      const job = await reportQueue.getJob(`report:${report._id}`);
      const progress = job ? job.progress : report.status === 'ready' ? 100 : 0;

      res.status(200).json({
        status: 'success',
        data: {
          reportId: report._id,
          state: report.status,
          progress,
          downloadUrl: report.downloadUrl || null
        }
      });
    } catch (err) {
      next(err);
    }
  });

  return router;
}

Step 3: Implement the Idempotent Standalone Worker Process

src/workers/report.worker.js 
import { Worker, UnrecoverableError } from 'bullmq';
import { createQueueConnection } from '../queues/report.queue.js';

export function startReportWorker({ reportRepository, reportBuilder, storage, mailer }) {
  const connection = createQueueConnection();

  const worker = new Worker(
    'reports',
    async (job) => {
      const { reportId, userId } = job.data;

      const claimed = await reportRepository.claimForProcessing(reportId);
      if (!claimed) {
        const existing = await reportRepository.findById(reportId);
        if (!existing) {
          throw new UnrecoverableError(`Report ${reportId} no longer exists`);
        }
        if (existing.status === 'ready') {
          return { skipped: true, reason: 'already_completed' };
        }
      }

      await job.updateProgress(20);
      const buffer = await reportBuilder.buildCsvBuffer(claimed);

      await job.updateProgress(70);
      const objectKey = `reports/${userId}/${reportId}.csv`;
      await storage.uploadBuffer(objectKey, buffer, 'text/csv');

      await reportRepository.markReady(reportId, objectKey);
      await job.updateProgress(90);

      await mailer.sendReportReadyEmail({ userId, reportId });
      await job.updateProgress(100);

      return { objectKey };
    },
    {
      connection,
      concurrency: 5
    }
  );

  worker.on('failed', async (job, err) => {
    console.error(`Job ${job?.id} failed on attempt ${job?.attemptsMade}:`, err.message);
    if (job && job.attemptsMade >= (job.opts.attempts || 1)) {
      await reportRepository.markFailed(job.data.reportId, err.message);
    }
  });

  const shutdown = async () => {
    await worker.close();
    await connection.quit();
    process.exit(0);
  };

  process.on('SIGTERM', shutdown);
  process.on('SIGINT', shutdown);

  return worker;
}

Step 4: Register a Centralized Recurring Schedule

src/queues/scheduler.js 
export async function registerScheduledJobs(reportQueue) {
  await reportQueue.upsertJobScheduler(
    'daily-cleanup-scheduler',
    { pattern: '0 2 * * *', tz: 'UTC' },
    {
      name: 'purge-expired-reports',
      data: { retentionDays: 30 }
    }
  );
}

Key Code Sections Explained

  • maxRetriesPerRequest: null: Required by BullMQ on ioredis connections so blocking worker commands wait reliably without throwing premature retry-limit errors.
  • HTTP 202 Accepted + jobId: `report:${report._id}`: Signals that processing was accepted asynchronously while deterministic IDs prevent duplicate queue entries on client double-clicks.
  • claimForProcessing(reportId) + UnrecoverableError: Atomic DB state transitions guard against duplicate execution if a worker crashes mid-job, while missing records abort retries immediately instead of burning 4 useless attempts.
  • removeOnComplete & removeOnFail Bounds: Prevents completed/failed job metadata from filling Redis RAM endlessly over months.
  • worker.close() on SIGTERM: Lets active jobs finish cleanly before the worker container stops during deployment.
06. Engineering Judgment

Implementation Options & Trade-Offs

Approach Durability Retry & Scheduling Best Fit
Inline HTTP Execution Tied to request socket None (fails user request) Fast operations (< 100ms) whose outcome the client needs immediately
Detached Fire-and-Forget Promise Lost on process crash/deploy None; unhandled errors risk memory leaks Only truly disposable metrics where dropping events is acceptable
BullMQ (Redis-Backed Queue) High (when Redis uses persistence + noeviction) Built-in backoff, priorities, cron schedulers, concurrency High-throughput Node.js apps already running Redis
pg-boss / Agenda (DB-Backed) Transactional with primary DB Good for low/moderate throughput Teams wanting zero extra Redis infrastructure at small-to-medium scale

When to Move Work to a Background Queue

  • Operation depends on slow external APIs (email, SMS, webhooks, AI APIs).
  • Task takes longer than ~300–500ms or is CPU-intensive (PDF/CSV/media processing).
  • Work needs reliable automatic retries or delayed execution.

When NOT to Queue

  • The client immediately needs the computed result to render the very next screen (e.g., login authentication or validating a promo code at checkout).
  • A simple 5ms DB insert where queue serialization and worker round-trips add needless complexity.
07. Production Readiness

Common Mistakes, Security & Reliability

Mistake 1: Storing Multi-Megabyte Blobs Inside Job Payloads

Performance risk: Passing entire base64 images or 5 MB JSON arrays in queue.add() bloats Redis RAM and slows every queue scan.

Fix: Store large files in object storage or records in your DB, and pass only compact IDs/keys inside the job payload.

Mistake 2: Running Queues on an Evicting Redis Instance

Data loss risk: If Redis uses allkeys-lru (appropriate for Day 4 caches), memory pressure silently deletes queued jobs!

Fix: Run queue Redis with maxmemory-policy noeviction and AOF persistence enabled, separate from cache Redis.

Mistake 3: Skipping Ownership Checks on Job Status Endpoints

Security risk: If GET /api/jobs/:jobId returns job details without verifying req.user.id === job.data.userId, attackers can enumerate job IDs to read other users' report links.

Fix: Always authorize status lookups against the authenticated owner.

Mistake 4: Retrying Forever or Retrying Invalid Data

Reliability risk: Infinite retries or retrying malformed payloads wastes worker slots and fills logs indefinitely.

Fix: Cap attempts (e.g., 3–5), use exponential backoff, and wrap non-retryable domain errors in UnrecoverableError.

Milestone Task: Offload User Welcome Email & Onboarding Export

  1. Keep password hashing and user DB insertion inside the HTTP request so validation errors still return 400/409 immediately.

10. Active Recall

Short-Answer Review Questions

Separating processes isolates the HTTP event loop from heavy CPU or memory spikes in PDF generation, media processing, or large exports. It also lets you autoscale worker replicas based on queue depth independently from web replicas based on HTTP traffic.

If a user double-clicks a submit button or a client retries a timed-out request, passing a deterministic key such as jobId: `invoice:${invoiceId}` ensures the queue detects an existing job with that ID and avoids inserting a second duplicate job into the queue.

By default, retaining every finished job hash forever causes Redis memory usage to grow indefinitely until the instance runs out of memory. Setting age and count bounds keeps recent debugging history available while pruning old entries automatically.

Keep synchronous: Checking user credentials during login or reserving inventory stock atomically at checkout, because the client cannot proceed without the immediate pass/fail decision. Move to background job: Sending the order confirmation email and generating the downloadable PDF receipt after the order is committed.

When a team already uses PostgreSQL and wants transactional outbox guarantees (inserting a domain record and enqueueing the job inside the exact same ACID SQL transaction) at moderate job throughput without operating and securing an extra Redis server.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: A worker handler sends an email first and then calls await invoiceRepo.markEmailSent(invoiceId). Whenever the database briefly times out on step 2, BullMQ retries the job and sends the customer the same email 4 times! Fix the handler logic.

Reference Solution 
export async function processInvoiceEmailJob(job, { invoiceRepo, mailer }) {
  const { invoiceId } = job.data;
  const invoice = await invoiceRepo.findById(invoiceId);
  if (!invoice) {
    throw new UnrecoverableError('Invoice missing');
  }
  if (invoice.emailStatus === 'sent') {
    return { skipped: true };
  }

  const sendResult = await mailer.sendInvoice({
    to: invoice.customerEmail,
    invoiceId: invoice._id,
    idempotencyKey: `invoice-email:${invoice._id}`
  });

  await invoiceRepo.markEmailSent(invoiceId, sendResult.messageId);
  return { messageId: sendResult.messageId };
}

Explanation: Checking emailStatus === 'sent' handles retries after a partial success, and passing an email-provider idempotency key (or recording a sending lock state with timestamp) protects even when the DB write fails right after sending.

Problem: Implement a pure JavaScript custom backoff function computeBackoffMs(attemptsMade, baseMs = 2000, maxMs = 60000) using exponential growth capped at maxMs plus ±20% jitter.

Reference Solution 
export function computeBackoffMs(attemptsMade, baseMs = 2000, maxMs = 60000) {
  const exp = Math.min(maxMs, baseMs * Math.pow(2, Math.max(0, attemptsMade - 1)));
  const jitterSpan = exp * 0.2;
  const offset = (Math.random() * 2 - 1) * jitterSpan;
  return Math.max(500, Math.round(exp + offset));
}

Problem: At 9:00 AM, your system enqueues 50,000 marketing newsletter emails. At 9:01 AM, a user requests a password-reset email and waits 18 minutes because all workers are busy with newsletters. How do you fix this architecturally?

Reference Architecture: Separate critical transactional jobs from bulk low-priority jobs using separate queues (auth-emails vs. bulk-newsletters) with dedicated worker pools—never let bulk batch jobs starve latency-sensitive user authentication flows. Within a single queue, job priorities also help, but separate queues guarantee dedicated worker capacity even during massive bulk spikes.

12. Takeaways

Day 5 Revision Summary

  • Offload slow work: Return 202 Accepted rapidly from Express and run heavy or unreliable tasks in persistent workers.
  • Durable queues beat in-memory promises: Redis-backed BullMQ (with noeviction) persists jobs across crashes and deployments.
  • Centralize schedules: Use queue schedulers for recurring/delayed tasks instead of per-instance setInterval timers.
  • Smart retries & idempotency: Combine exponential backoff, UnrecoverableError for permanent faults, deterministic jobIds, and atomic DB status claims.
  • Monitor queue health: Watch waiting depth, failure rates, job durations, and expose authorized status polling.
