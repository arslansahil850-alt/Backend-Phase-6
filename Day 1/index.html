Day 01 Architecture & Design

Advanced Backend Architecture and Design Patterns

Small Express APIs often start as a few route files with database queries directly inside request handlers. That works for prototypes, but collapses rapidly as business rules, validation, authentication, error handling, and team size grow. Today you will learn how to structure backend systems into clear boundaries that remain testable, replaceable, and maintainable under production change.

Prerequisites

Node.js, Express routing and middleware, async/await, HTTP status codes, and basic CRUD operations.

Connection to Phase 6

Every topic ahead — caching, queues, testing, logging, and scaling — relies on the clean layer boundaries established today.

Practical Output

Refactor a coupled Express route handler into distinct routes, controllers, services, repositories, and a composition root.

01. Foundation

What You Will Learn & Objectives

Architecture is not about adding folders for appearance; it is about controlling coupling (how tightly modules depend on each other) and cohesion (how clearly each module owns a single responsibility).

Compare Structural Paradigms

Distinguish classic monoliths, modular monoliths, layered architectures, and MVC variations for Node.js backends.

Enforce Separation of Concerns

Isolate HTTP transport handling, domain business logic, and database persistence into dedicated layers.

Apply Service & Repository Patterns

Decouple business workflows from ORM/driver specifics so logic is easy to test and evolve.

Use Dependency Injection & SOLID

Wire collaborators explicitly and apply SOLID principles pragmatically in idiomatic JavaScript.

02. Deep Dive

Core Architectural Concepts

1. Monolithic vs. Modular Monolith Architecture

A monolith deploys the entire backend as a single process and codebase. Contrary to common hype, monoliths are often the best starting point because they have zero network latency between modules, simple atomic database transactions, and straightforward deployment.

The failure mode of a disorganized monolith (a "big ball of mud") is not single deployment—it is unrestricted cross-imports where billing code queries user tables directly and auth middleware mutates order state. A modular monolith keeps a single deployable process while organizing code into strict domain modules (such as orders, users, billing) that communicate only through public module service interfaces.

2. Layered Architecture

Layered architecture slices an application horizontally by technical responsibility. Requests enter at the top and travel downward through strictly ordered layers:

  • Presentation / Transport Layer (Routes & Controllers): Parses HTTP params, headers, and bodies; invokes validation; sends HTTP status codes and JSON responses.
  • Application / Business Logic Layer (Services): Orchestrates use cases, enforces domain rules (e.g., discount eligibility, stock reservation), and remains unaware of HTTP req or res objects.
  • Data Access Layer (Repositories): Executes queries against MongoDB, PostgreSQL, or external APIs and maps raw records into predictable domain structures.
  • Infrastructure / Cross-Cutting Layer: Configuration, loggers, database connection pools, cryptographic utilities, and error classes shared cleanly across layers.

3. MVC and Separation of Concerns

Classic MVC (Model-View-Controller) separates data/rules (Model), rendered UI (View), and input coordination (Controller). In REST or JSON APIs, there is no server-rendered HTML View—the JSON serializer acts as the representation.

A frequent mistake in Express MVC apps is stuffing all business rules inside Mongoose/Sequelize Models ("fat models") or inside Controllers ("fat controllers"). Adding a dedicated Service Layer solves this: Controllers handle HTTP only, Services hold business rules, and Models/Repositories define schemas and persistence queries.

4. Service and Repository Patterns

The Service Pattern encapsulates a complete business operation—such as createOrder or resetPassword—independently of how it was triggered (HTTP endpoint, CLI script, or background worker).

The Repository Pattern wraps persistence behind collection-like methods such as findById(id), findActiveByEmail(email), or save(entity). Your service never constructs raw Mongoose filters or SQL strings; it calls repository methods. This makes unit testing services trivial using an in-memory fake repository, and isolates schema or database changes to one place.

5. Dependency Injection (DI) in JavaScript

If a service executes const userRepo = require('./user.repository') internally, it hardcodes its dependency. Swapping a real database repository for a mock in tests becomes awkward, requiring module-loader monkey patching.

Dependency Injection flips control: instead of creating its own dependencies, a module receives them as constructor parameters or factory arguments. In JavaScript, you do not need heavy decorator frameworks—simple constructor injection or factory functions assembled in a single composition root (container.js or app.js) give you full DI benefits with zero magic.

6. SOLID Principles Applied to Backend Code

S — Single Responsibility

A controller parses HTTP; a service enforces business rules; a repository persists data. Each module has one primary reason to change.

O — Open / Closed

Add new notification channels (email, SMS, webhook) or payment gateways by adding new strategy classes without rewriting core checkout logic.

L — Liskov Substitution

An in-memory repository and a MongoDB repository must honor the same method signatures, return shapes, and error contracts.

I — Interface Segregation

Keep repository and service contracts focused. Do not force a read-only analytics service to depend on write-heavy user mutation methods.

D — Dependency Inversion

High-level business services depend on abstract repository contracts (expected method shapes), not directly on Mongoose models or SQL drivers.

7. Maintainable Folder Structures

Two major folder layouts exist in Node.js backends: grouping by technical role (controllers/, services/, repositories/) and grouping by domain feature (modules/orders/, modules/users/). Small services work well with role-based folders, while medium-to-large backends scale far better with feature-based modular folders where everything needed to change a domain lives side by side.

8. Choosing the Right Architecture

Over-engineering a tiny CRUD service with 15 abstraction layers slows delivery without benefit. Under-engineering a financial ledger or multi-tenant SaaS creates costly bugs. Choose based on team size, domain rule complexity, expected lifespan, and rate of requirement change.

03. Mechanics

How a Layered Request Flows End to End

  1. Route & Middleware: Express matches the HTTP method and path, applies authentication and input validation middleware, and forwards control to the controller.
  2. Controller: Extracts sanitized parameters (req.body, req.params, req.user), calls the appropriate service method, and translates the result into an HTTP status code and JSON envelope.
  3. Service: Validates business invariants (such as checking inventory, calculating totals, preventing duplicate states), coordinates one or more repositories, and throws domain errors when rules fail.
  4. Repository: Translates domain calls into database commands (Mongoose, PostgreSQL pool, or in-memory store), returning plain objects or domain models without leaking driver internals upward.
  5. Centralized Error Middleware: Catches operational errors (AppError with status 400, 404, 409) vs. unexpected programmer errors (500), sending consistent safe responses.

05. Step-by-Step Implementation

Refactoring a Coupled Express Endpoint into Clean Layers

Consider a typical unlayered Express endpoint that mixes request validation, pricing rules, stock checks, Mongoose queries, and HTTP error responses in a single file.

Before: Tightly Coupled Route Handler 
import express from 'express';
import Order from '../models/Order.js';
import Product from '../models/Product.js';

const router = express.Router();

router.post('/orders', async (req, res) => {
  try {
    const { productId, quantity } = req.body;
    if (!productId || !quantity || quantity < 1) {
      return res.status(400).json({ error: 'Invalid input' });
    }
    const product = await Product.findById(productId);
    if (!product) {
      return res.status(404).json({ error: 'Product not found' });
    }
    if (product.stock < quantity) {
      return res.status(409).json({ error: 'Insufficient stock' });
    }
    product.stock -= quantity;
    await product.save();
    const total = product.price * quantity;
    const order = await Order.create({
      userId: req.user.id,
      productId,
      quantity,
      total
    });
    res.status(201).json(order);
  } catch (err) {
    res.status(500).json({ error: 'Server error' });
  }
});

export default router;

Step 1: Define a Shared Operational Error Class

Services should never import Express's res object. Instead, they throw structured domain errors carrying an HTTP-friendly status code and machine-readable code.

src/shared/errors/AppError.js 
export class AppError extends Error {
  constructor(message, statusCode = 500, code = 'INTERNAL_ERROR') {
    super(message);
    this.name = 'AppError';
    this.statusCode = statusCode;
    this.code = code;
    this.isOperational = true;
    Error.captureStackTrace(this, this.constructor);
  }
}

Step 2: Create Focused Repositories

Each repository hides database query syntax and returns plain JavaScript objects or consistent domain records. Notice how stock deduction uses an atomic conditional update (stock: { $gte: quantity }) to prevent race-condition overselling.

src/modules/orders/order.repository.js 
export class MongoOrderRepository {
  constructor(OrderModel) {
    this.OrderModel = OrderModel;
  }

  async create(orderData) {
    const doc = await this.OrderModel.create(orderData);
    return doc.toObject();
  }

  async findByUserId(userId) {
    return this.OrderModel.find({ userId }).sort({ createdAt: -1 }).lean();
  }
}

export class MongoProductRepository {
  constructor(ProductModel) {
    this.ProductModel = ProductModel;
  }

  async findById(productId) {
    return this.ProductModel.findById(productId).lean();
  }

  async reserveStock(productId, quantity) {
    return this.ProductModel.findOneAndUpdate(
      { _id: productId, stock: { $gte: quantity } },
      { $inc: { stock: -quantity } },
      { new: true }
    ).lean();
  }
}

Step 3: Implement the Pure Service Layer with Dependency Injection

OrderService receives repositories in its constructor. It contains zero Express imports and zero Mongoose queries, making business rules crystal clear and independently testable.

src/modules/orders/order.service.js 
import { AppError } from '../../shared/errors/AppError.js';

export class OrderService {
  constructor({ orderRepository, productRepository }) {
    this.orderRepository = orderRepository;
    this.productRepository = productRepository;
  }

  async placeOrder({ userId, productId, quantity }) {
    if (!Number.isInteger(quantity) || quantity < 1) {
      throw new AppError('Quantity must be a positive integer', 400, 'INVALID_QUANTITY');
    }

    const product = await this.productRepository.findById(productId);
    if (!product) {
      throw new AppError('Product not found', 404, 'PRODUCT_NOT_FOUND');
    }

    const reserved = await this.productRepository.reserveStock(productId, quantity);
    if (!reserved) {
      throw new AppError('Insufficient stock available', 409, 'INSUFFICIENT_STOCK');
    }

    const totalCents = Math.round(reserved.priceCents * quantity);
    return this.orderRepository.create({
      userId,
      productId,
      quantity,
      totalCents,
      status: 'confirmed'
    });
  }

  async listUserOrders(userId) {
    return this.orderRepository.findByUserId(userId);
  }
}

Step 4: Build the Thin Controller & Route Binding

The controller adapts HTTP inputs into service parameters, passes errors to Express's error middleware via next(err), and formats the HTTP response.

src/modules/orders/order.controller.js & order.routes.js 
import express from 'express';

export class OrderController {
  constructor(orderService) {
    this.orderService = orderService;
  }

  create = async (req, res, next) => {
    try {
      const order = await this.orderService.placeOrder({
        userId: req.user.id,
        productId: req.body.productId,
        quantity: Number(req.body.quantity)
      });
      res.status(201).json({ status: 'success', data: order });
    } catch (err) {
      next(err);
    }
  };

  listMine = async (req, res, next) => {
    try {
      const orders = await this.orderService.listUserOrders(req.user.id);
      res.status(200).json({ status: 'success', data: orders });
    } catch (err) {
      next(err);
    }
  };
}

export function createOrderRouter(orderController, authMiddleware) {
  const router = express.Router();
  router.use(authMiddleware);
  router.post('/', orderController.create);
  router.get('/', orderController.listMine);
  return router;
}

Step 5: Assemble Dependencies in the Composition Root

src/container.js & src/shared/middlewares/errorHandler.js 
import OrderModel from './modules/orders/order.model.js';
import ProductModel from './modules/products/product.model.js';
import { MongoOrderRepository, MongoProductRepository } from './modules/orders/order.repository.js';
import { OrderService } from './modules/orders/order.service.js';
import { OrderController } from './modules/orders/order.controller.js';

export function buildContainer() {
  const orderRepository = new MongoOrderRepository(OrderModel);
  const productRepository = new MongoProductRepository(ProductModel);
  const orderService = new OrderService({ orderRepository, productRepository });
  const orderController = new OrderController(orderService);

  return { orderController, orderService };
}

export function errorHandler(err, req, res, next) {
  const statusCode = err.isOperational ? err.statusCode : 500;
  const payload = {
    status: 'error',
    code: err.isOperational ? err.code : 'INTERNAL_ERROR',
    message: err.isOperational ? err.message : 'An unexpected error occurred'
  };
  res.status(statusCode).json(payload);
}

Key Code Sections Explained

  • Arrow class methods (create = async (req, res, next) =>): Preserves lexical this binding when Express passes orderController.create as a route callback without manual .bind(controller).
  • Integer cents (totalCents): Avoids IEEE-754 floating-point rounding bugs common in naive monetary calculations (e.g., 0.1 + 0.2 !== 0.3).
  • .lean() in Mongoose repositories: Returns plain JavaScript objects instead of heavy hydrated Mongoose documents, reducing memory overhead and preventing accidental model mutation inside services.
  • Safe Error Masking: Unknown non-operational errors never leak database stack traces or driver messages to API clients.
06. Engineering Judgment

Use Cases, Alternatives, and Trade-Offs

Good architects evaluate architectural styles against actual project constraints rather than following trends blindly.

Architecture Style Best Fit Strengths Limitations & Risks
Simple Route-Model (Flat MVC) Hackathons, internal scripts, 3–5 endpoint prototypes Fastest initial velocity, minimal boilerplate High coupling; logic duplicates quickly; hard to unit test without DB
Layered Modular Monolith Most production APIs, SaaS backends, mid-to-large teams Clear boundaries, easy testing via DI, atomic DB transactions Requires team discipline to prevent cross-module shortcut imports
Hexagonal / Clean Architecture Complex domains (fintech, compliance, multi-adapter systems) Domain completely insulated from frameworks and databases Extra mapper/DTO boilerplate; overkill for basic CRUD
Microservices Large orgs needing independent scaling/deploy cadence per team Fault isolation, independent tech stacks and scaling Distributed transactions, network latency, complex observability & ops

When to Use Layered + DI Architecture

  • Business workflows involve validation, multi-step state transitions, or external integrations.
  • Multiple team members edit the codebase concurrently.
  • You want fast unit tests that run without spinning up MongoDB or PostgreSQL on every check.
  • The same business logic may later be invoked by a background worker or CLI tool.

When NOT to Over-Abstract

  • Building a throwaway spike or 2-route webhook forwarder where 6 files add pure friction.
  • Creating pass-through service methods that blindly wrap single-line repository calls with zero rules and zero anticipated growth.
  • Introducing complex IoC reflection containers when plain constructor arguments suffice.
07. Production Readiness

Common Mistakes, Security, Reliability & Performance

Mistake 1: Passing req and res into the Service Layer

Why it hurts: Ties business logic to Express HTTP transport, breaking reuse in BullMQ workers, cron tasks, or WebSocket handlers.

Fix: Extract plain primitive or DTO inputs in the controller and return plain data or throw AppError from the service.

Mistake 2: Circular Dependencies Between Services

Why it hurts: OrderService imports UserService while UserService imports OrderService, causing undefined imports at runtime.

Fix: Keep service graphs acyclic (DAG), extract shared logic into a lower-level helper/service, or communicate via domain events.

Mistake 3: Anemic Pass-Through Layers Without Validation Boundaries

Why it hurts: Spreading partial validation across routes, controllers, and schemas leaves gaps where invalid payloads reach databases.

Fix: Validate input shape and types at the HTTP boundary (e.g., Zod/Joi middleware), and enforce domain invariants (stock, permissions, state machines) inside services.

Mistake 4: Leaking Internal Errors or Sensitive Fields

Why it hurts: Returning raw database objects exposes password hashes or internal flags; returning raw driver errors leaks table/collection names.

Fix: Project explicit public DTO fields in repositories/controllers and restrict error responses to safe operational messages in production.

10. Active Recall

Short-Answer Review Questions

Cohesion measures how closely related the responsibilities inside a single module are. Coupling measures how heavily one module depends on the internal details of another. Well-designed backends aim for high cohesion inside each module and loose coupling between modules.

A composition root (such as container.js or startup wiring in app.js) is the single top-level location where concrete repositories, external clients, services, and controllers are instantiated and wired together. Lower layers never import or construct their collaborators directly.

Microservices trade in-process function calls for network calls, introducing partial failures, distributed tracing complexity, eventual consistency across separate databases, and heavy deployment pipelines. A modular monolith delivers clean domain separation without distributed systems overhead until scale or team boundaries truly demand splitting.

Define a consistent notifier interface (e.g., send({ to, subject, body })) and inject a map or array of channel providers (EmailNotifier, SmsNotifier, WebhookNotifier) into NotificationService. Adding a new channel requires adding a new provider class and registering it in the composition root without modifying core service logic.

.lean() returns plain JavaScript objects rather than Mongoose Document instances containing .save(), change-tracking getters, and ORM state. This guarantees that services cannot accidentally trigger hidden database writes and keeps the service layer unaware of Mongoose internals.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: A junior developer wrote BillingService.charge(req, res) which calls StripeClient created directly inside the method and sends res.status(402).json({ err }) on decline. Explain three architectural flaws and show the corrected signature and behavior.

Reference Solution 
export class BillingService {
  constructor(paymentGateway, invoiceRepository) {
    this.paymentGateway = paymentGateway;
    this.invoiceRepository = invoiceRepository;
  }

  async chargeInvoice({ invoiceId, paymentMethodId }) {
    const invoice = await this.invoiceRepository.findById(invoiceId);
    if (!invoice) {
      throw new AppError('Invoice not found', 404, 'INVOICE_NOT_FOUND');
    }
    const receipt = await this.paymentGateway.charge({
      amountCents: invoice.amountCents,
      paymentMethodId
    });
    if (!receipt.approved) {
      throw new AppError('Payment declined', 402, 'PAYMENT_DECLINED');
    }
    return this.invoiceRepository.markPaid(invoiceId, receipt.transactionId);
  }
}

Three flaws fixed: (1) Removed req/res transport coupling, (2) injected paymentGateway and invoiceRepository instead of instantiating inside the method, and (3) threw structured AppError instead of sending HTTP responses from the service.

Problem: Implement an InMemoryProductRepository matching MongoProductRepository's contract (findById and atomic-style reserveStock) so OrderService can be tested with zero database dependency.

Reference Solution 
export class InMemoryProductRepository {
  constructor(initialProducts = []) {
    this.store = new Map(
      initialProducts.map((item) => [item._id, { ...item }])
    );
  }

  async findById(productId) {
    const item = this.store.get(productId);
    return item ? { ...item } : null;
  }

  async reserveStock(productId, quantity) {
    const item = this.store.get(productId);
    if (!item || item.stock < quantity) {
      return null;
    }
    item.stock -= quantity;
    return { ...item };
  }
}

Problem: Design the module structure and interfaces for a system that sends order confirmations via Email immediately, and later needs SMS and Push notifications added without changing OrderService.

Reference Architecture: Inject a single notificationPublisher port into OrderService. At startup, NotificationDispatcher receives an array/map of channel adapters (EmailChannel, SmsChannel, PushChannel), each implementing supports(preference) and deliver(payload). Adding a new channel is an additive change (Open/Closed Principle) wired in container.js, leaving OrderService untouched.

12. Takeaways

Day 1 Revision Summary

  • Modular monoliths provide clean domain separation without premature microservice network and operational overhead.
  • Layered separation assigns HTTP parsing to controllers, business rules to services, and query mechanics to repositories.
  • Dependency Injection in JavaScript requires no complex frameworks—pass collaborators via constructors/factories from a single composition root.
  • SOLID principles translate directly to backend Node.js: focused layers (SRP), pluggable adapters (OCP), consistent repository contracts (LSP), lean interfaces (ISP), and abstract dependencies (DIP).
  • Operational error handling separates predictable client/domain failures from unexpected crashes so sensitive internals are never exposed.
