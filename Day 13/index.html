Day 13 Quality Assurance & Verification

Advanced Backend Testing

Manual curl checks do not catch subtle regressions in authorization boundaries, atomic database updates, error formatting, or edge-case failures weeks later. Today you will learn how unit, integration, and end-to-end tests work together, how to mock external gateways while testing real database queries, how to enforce test isolation, and how to test authentication, RBAC, and ownership flows reliably.

Connection to Days 1 & 8

Day 1's Dependency Injection makes service unit tests effortless, while Day 8's auth/IDOR gates become mandatory integration test assertions.

Core Principle

Test observable behavior and failure paths against realistic boundaries—do not mock everything until tests only verify your own mocks.

Practical Output

Write a clean Node.js test suite combining fast DI unit tests and Supertest API integration tests with isolated test database cleanup and auth checks.

02. Deep Dive

Core Backend Testing Concepts

1. Unit, Integration, and End-to-End Testing

  • Unit Tests: Verify a single pure helper or injected service class in isolation (milliseconds, zero network/disk I/O). Great for pricing rules, state transitions, parsers, and edge-case business branches.
  • Integration Tests: Exercise multiple real components working together—for example, sending a real HTTP request through Express routing, validation middleware, controller, service, repository, and a real test database. For APIs, integration tests catch the bugs unit tests miss (broken middleware ordering, Mongoose/SQL query typos, serialization errors).
  • End-to-End (E2E) Tests: Exercise complete multi-step user journeys (register → login → upload → background worker → webhook) across a fully running environment. Keep E2E tests focused on critical flows because they are slowest and most sensitive to timing.

2. Testing Controllers, Services, and Database Operations

Export your configured Express app separately from server.listen() so tests can pass app directly to supertest(app) without port conflicts. Test business logic directly via fast service unit tests (injecting in-memory repositories), and verify real Express middleware, status codes, JSON envelopes, and MongoDB/SQL queries via Supertest integration tests.

3. Mocking and Stubbing Boundaries

A stub provides canned responses (e.g., making a fake payment gateway return { approved: false }); a mock also records/asserts interactions. Mock external boundaries you do not own—third-party payment gateways, SMTP emailers, SMS providers, or S3 in fast suites—so tests stay deterministic and offline-capable.

Warning: Avoid mocking Mongoose/PostgreSQL inside integration tests. If you mock every database call, your suite will pass even when a query contains a syntax error or fails an index/unique constraint!

4. Test Databases and Test Isolation

Every test must run cleanly in isolation—whether executed alone, in reverse order, or in parallel:

  • Dedicated Ephemeral DB: Never run automated tests against development or production databases! Use a separate local/Docker test database, Testcontainers, or mongodb-memory-server.
  • Clean State Hooks: Truncate/clear collections in beforeEach or wrap SQL tests in rolled-back transactions, and create unique user/fixture records per test rather than relying on fragile shared global seed state.

5. Authentication and Authorization Tests

Every protected endpoint needs explicit negative security assertions:

  • Unauthenticated request → 401 Unauthorized.
  • Expired or tampered token → 401 Unauthorized.
  • Authenticated user lacking required role/permission → 403 Forbidden.
  • Authenticated User B requesting or editing User A's private resource (IDOR check) → 403 Forbidden (or safe 404).

6. Edge Cases, Failure Scenarios & Coverage Limits

Happy-path tests ("POST returns 201") catch less than half of real bugs. Explicitly test boundary limits (limit=0, limit=99999), missing/wrong-type fields, duplicate unique keys (409), downstream timeouts, and concurrent conflicting writes (Promise.all).

Test Coverage Limits: Code coverage (e.g., node --test --experimental-test-coverage or Jest --coverage) only proves a line executed—not that you asserted the right behavior, checked authorization, or handled empty/concurrent inputs. Treat coverage as a tool to spot untested branches, never as a vanity target that encourages assertion-free tests.

7. Continuous Testing Concepts

Tests only protect teams when they run automatically on every commit and pull request (Day 16 CI pipelines). Keep fast unit and integration suites under 1–2 minutes so developers run them locally before pushing and CI blocks broken merges immediately.

03. Mechanics

Anatomy of an Isolated API Integration Test Run

  1. Suite Boot (before): Connect to a dedicated isolated test database (or ephemeral container), apply schema/indexes, and build the Express app with stubbed external email/payment gateways.
  2. Per-Test Reset (beforeEach): Clear collections/tables and reset stub call histories so Test 2 never sees rows inserted by Test 1.
  3. Arrange, Act, Assert: Create test user fixtures/tokens (Arrange), send HTTP calls via supertest(app) (Act), and verify HTTP status, JSON response shape, and persisted database state (Assert).
  4. Teardown (after): Close DB connections, Redis clients, and worker pools cleanly so the test runner exits with code 0 without hanging open handles.

05. Step-by-Step Implementation

Building a Node.js Unit & Supertest Integration Suite

Using Node.js's built-in node:test runner and node:assert/strict (with Jest/Vitest following nearly identical describe/it structure) plus supertest keeps dependencies minimal and fast.

Step 1: Fast Unit Tests for Service Logic & Edge Cases

tests/unit/order.service.test.js 
import { describe, it } from 'node:test';
import assert from 'node:assert/strict';
import { OrderService } from '../../src/modules/orders/order.service.js';

function createFakeRepos({ stock = 5, priceCents = 1500 } = {}) {
  const products = new Map([['prod_1', { _id: 'prod_1', stock, priceCents }]]);
  const orders = [];
  return {
    productRepository: {
      async findById(id) {
        return products.get(id) || null;
      },
      async reserveStock(id, qty) {
        const item = products.get(id);
        if (!item || item.stock < qty) {
          return null;
        }
        item.stock -= qty;
        return { ...item };
      }
    },
    orderRepository: {
      async create(data) {
        const created = { _id: `ord_${orders.length + 1}`, ...data };
        orders.push(created);
        return created;
      },
      async findByUserId(userId) {
        return orders.filter((o) => o.userId === userId);
      }
    }
  };
}

describe('OrderService unit tests', () => {
  it('places an order and computes integer totalCents accurately', async () => {
    const repos = createFakeRepos({ stock: 5, priceCents: 1999 });
    const service = new OrderService(repos);

    const order = await service.placeOrder({
      userId: 'user_1',
      productId: 'prod_1',
      quantity: 3
    });

    assert.equal(order.totalCents, 5997);
    assert.equal(order.status, 'confirmed');
  });

  it('rejects insufficient stock with 409 operational error', async () => {
    const repos = createFakeRepos({ stock: 1, priceCents: 1000 });
    const service = new OrderService(repos);

    await assert.rejects(
      () => service.placeOrder({ userId: 'user_1', productId: 'prod_1', quantity: 2 }),
      (err) => err.statusCode === 409 && err.code === 'INSUFFICIENT_STOCK'
    );
  });

  it('prevents concurrent overselling when two requests race for last item', async () => {
    const repos = createFakeRepos({ stock: 1, priceCents: 1000 });
    const service = new OrderService(repos);

    const results = await Promise.allSettled([
      service.placeOrder({ userId: 'u1', productId: 'prod_1', quantity: 1 }),
      service.placeOrder({ userId: 'u2', productId: 'prod_1', quantity: 1 })
    ]);

    const fulfilled = results.filter((r) => r.status === 'fulfilled');
    const rejected = results.filter((r) => r.status === 'rejected');
    assert.equal(fulfilled.length, 1);
    assert.equal(rejected.length, 1);
    assert.equal(rejected[0].reason.statusCode, 409);
  });
});

Step 2: Isolated Supertest Integration Tests (AuthN, AuthZ, IDOR & DB)

tests/integration/documents.api.test.js 
import { describe, it, before, beforeEach, after } from 'node:test';
import assert from 'node:assert/strict';
import request from 'supertest';
import mongoose from 'mongoose';
import jwt from 'jsonwebtoken';
import { createApp } from '../../src/app.js';

function signTestToken(userId, roles = ['editor']) {
  return jwt.sign(
    { roles, tv: 1 },
    process.env.JWT_ACCESS_SECRET,
    {
      algorithm: 'HS256',
      subject: userId,
      issuer: process.env.JWT_ISSUER,
      audience: process.env.JWT_AUDIENCE,
      expiresIn: '5m'
    }
  );
}

describe('Documents API integration tests', () => {
  let app;

  before(async () => {
    await mongoose.connect(process.env.TEST_MONGO_URI);
    app = createApp({
      mailerStub: { send: async () => ({ queued: true }) }
    });
  });

  beforeEach(async () => {
    const collections = await mongoose.connection.db.collections();
    for (const col of collections) {
      await col.deleteMany({});
    }
  });

  after(async () => {
    await mongoose.disconnect();
  });

  it('returns 401 when Authorization header is missing', async () => {
    const res = await request(app).get('/api/v1/documents');
    assert.equal(res.status, 401);
  });

  it('returns 403 when viewer role attempts to create a document', async () => {
    const viewerToken = signTestToken('65f000000000000000000001', ['viewer']);
    const res = await request(app)
      .post('/api/v1/documents')
      .set('Authorization', `Bearer ${viewerToken}`)
      .send({ title: 'Spec Draft' });

    assert.equal(res.status, 403);
  });

  it('blocks User B from editing User A document (IDOR check)', async () => {
    const userAToken = signTestToken('65f000000000000000000001', ['editor']);
    const userBToken = signTestToken('65f000000000000000000002', ['editor']);

    const created = await request(app)
      .post('/api/v1/documents')
      .set('Authorization', `Bearer ${userAToken}`)
      .send({ title: 'Private Roadmap' });
    assert.equal(created.status, 201);

    const docId = created.body.data.id;
    const hijackAttempt = await request(app)
      .patch(`/api/v1/documents/${docId}`)
      .set('Authorization', `Bearer ${userBToken}`)
      .send({ title: 'Tampered' });

    assert.equal(hijackAttempt.status, 403);
  });
});

Key Code Sections Explained

  • Promise.allSettled Concurrency Test: Actively verifies that racing two checkouts for the last unit yields 1 success and 1 clean 409 rejection.
  • beforeEach Collection Cleanup: Guarantees zero shared state leaks between tests so any test can run standalone or in any order.
  • after(() => mongoose.disconnect()): Closes database sockets cleanly so CI test runs never hang after finishing.
  • Negative Security Assertions: Explicitly checks 401 missing auth, 403 insufficient role permission, and 403 cross-user IDOR attempts.
06. Engineering Judgment

Test Types & Framework Trade-Offs

Test Level Speed What It Verifies Mock / External Strategy
Unit Test ~1–5ms per test Business calculations, state machines, validators, policy functions Inject in-memory fake repositories and stub gateways
API Integration Test ~20–100ms per test Express routes, middleware order, auth, DB queries, error serialization Real Express app + real isolated test DB; stub external HTTP SaaS APIs
End-to-End (E2E) Seconds per flow Full multi-service deployment (API + worker + broker + storage) Ephemeral Docker Compose stack or staging sandbox

Node Built-in Test Runner vs. Jest / Vitest

node --test requires zero extra dependencies, starts instantly, and ships built-in coverage/mocking in modern Node.js. Jest and Vitest add rich snapshot matchers, parallel worker pools, module mocking ergonomics, and watch dashboards—pick whichever integrates cleanest with your team and CI pipeline.

Test Coverage Philosophy

Focus coverage on critical paths: money calculations, auth/ownership gates, state transitions, and failure fallbacks. A 75% suite testing real invariants and negative security boundaries beats a brittle 98% suite full of trivial getter tests.

07. Production Readiness

Common Testing Mistakes & Flakiness Traps

Mistake 1: Order-Dependent Tests Sharing State

Flakiness risk: Test 2 relies on a user created by Test 1—running Test 2 alone or in parallel fails unpredictably.

Fix: Reset test database state before each test and create explicit test fixtures inside each test case.

Mistake 2: Mocking the Database in Integration Tests

False confidence: Stubbing OrderModel.find hides broken query filters, missing required fields, unique constraint crashes, and aggregation bugs.

Fix: Mock databases in fast unit tests; hit a real isolated test database in API integration tests.

Mistake 3: Using Hardcoded setTimeout(500) for Async Tests

Flakiness risk: Tests pass on a fast laptop and flake intermittently on slower CI runners when a worker takes 650ms.

Fix: Poll with bounded retry helpers (e.g., check every 20ms up to 3s) or await deterministic promises/events directly.

Mistake 4: Pointing Test Config at Development or Production Databases

Data loss disaster: Running beforeEach cleanup against a shared database wipes real data!

Fix: Guard test cleanup helpers explicitly (abort if NODE_ENV !== 'test' or if DB name lacks _test).

Milestone Task: Build a Complete Test Suite for an API

Create a test suite covering a Tasks or Orders Express API using node:test (or Jest/Vitest) and supertest:

  1. Write 4+ unit tests for your service layer using an in-memory repository, verifying pricing/validation logic and failure branches.
  2. Write 5+ integration tests against createApp() and an isolated test database (guarding NODE_ENV === 'test' before truncation).

10. Active Recall

Short-Answer Review Questions

Most backend bugs occur at boundaries: route validation schemas, auth middleware order, JSON serialization, error mapping, and database queries. Supertest integration tests exercise that full vertical slice in tens of milliseconds.

A stub provides predetermined canned return values or errors to control test inputs (e.g., simulating a gateway timeout). A mock also records how it was called so tests can verify specific interactions.

Tests coupled to internal private function calls break every time you refactor clean code even though external behavior stayed 100% valid. Testing HTTP contracts and persisted state lets you refactor internals confidently.

(1) Missing/invalid token returns 401; (2) valid token lacking required role/permission returns 403; (3) valid user targeting another user's resource (IDOR) returns 403/404; (4) invalid request payload fails validation cleanly with 400/422.

Full E2E suites require spinning up multiple services, workers, or browsers, making them much slower, harder to debug when a step fails, and more prone to timing flakiness. Cover core user journeys with E2E and push edge cases down into integration and unit tests.

11. Engineering Drills

Coding, Debugging & System-Design Challenges

Problem: Test A creates a user ali@test.com and asserts 201. Test B assumes ali@test.com already exists and logs in. When Test B runs first or alone, it fails with 401! How do you fix it cleanly?

Reference Solution: Make each test self-contained: wipe the DB in beforeEach, create a fresh fixture helper createAndLoginUser(app, overrides) called explicitly inside Test B's Arrange phase, and avoid implicit cross-test dependencies.

Problem: Write a clean async helper waitUntil(predicateFn, { timeoutMs = 3000, intervalMs = 25 }) that replaces flaky fixed setTimeout waits when testing eventual background job completion.

Reference Solution 
export async function waitUntil(predicateFn, { timeoutMs = 3000, intervalMs = 25 } = {}) {
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    const result = await predicateFn();
    if (result) {
      return result;
    }
    await new Promise((resolve) => setTimeout(resolve, intervalMs));
  }
  throw new Error(`Condition not met within ${timeoutMs}ms`);
}

Problem: You integrate an external Stripe-like payment API. List 4 edge/failure scenarios your automated suite should test using a stubbed gateway without ever hitting the real payment provider.

Reference Test Cases: (1) Gateway declines card → order stays unpaid, stock reservation rolls back, API returns 402; (2) Gateway times out after 5s → safe 503/504 without crashing Express; (3) Client retries with identical Idempotency-Key → gateway stub called only once and same receipt returned; (4) Invalid webhook HMAC signature → rejected with 401 before mutating order state.

12. Takeaways

Day 13 Revision Summary

  • Testing layers: Fast unit tests guard domain rules; Supertest + real test DB integration tests guard routes, auth, and queries; E2E covers critical journeys.
  • Smart mocking: Stub external third-party APIs; avoid mocking your own database inside integration tests.
  • Strict isolation: Reset test DB state in beforeEach, guard against non-test URIs, and close all sockets in after.
  • Security & edge cases: Explicitly test 401, 403 RBAC, IDOR ownership, validation errors, timeouts, and concurrent races.
  • Coverage realism: Use coverage reports to spot missed branches, not as a substitute for strong assertions.
